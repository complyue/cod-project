# CoD 设计纲领：Regional GADT 语义数据库与分阶段原生执行

日期：2026-09-16  
状态：长期设计纲领；定义目标与架构约束，不是已实现功能清单。

本文用于指导语言、存储、运行时、编译器和开发工具的共同演进。核心目标是确定的；具体类型理论、二进制布局、文本语法、事务算法和工具协议仍需专门设计。文中的伪签名和操作名称仅用于说明语义，不是已经发布的 API。

## 1. 项目定位

**CoD 以 regional GADT 图统一承载领域知识、领域数据和业务逻辑意图，以 DBMR 保存高度结构化的持久语义单元，在同一个运行时中即时组合多个 domain 的 regions，并用 LLVM 实现面向差异化执行环境的原生 effects handler。业务程序不因执行环境的变化而被改写。**

系统同时面向机器、人类和智能体：机器直接使用结构化语义图，以低开销访问和执行；人类能够迅速获得可阅读、可导航、可编辑的文本源码；智能体能够通过具有语义约束的编辑机制完成局部、可验证、可审阅的修改。

交互式运行 C++ 不是最终目的。C++、现有 REPL、包管理和工具链自举是验证与实现上述目标的设施，不定义最终业务语言的边界。

### 核心原则

1. **业务意图是一等对象。** 业务程序完整地表达在有类型的 regional GADT 图中，而不是隐藏在宿主语言回调或原生调用栈里。
2. **领域语义是一等对象。** ontology、类型关系、事实、程序和 effects 契约均具有可识别、可查询、可检查的结构。
3. **集成不侵入原程序。** 通过显式的领域映射、类型检查和 handler 绑定完成环境适配，不为每个执行环境重写业务图。
4. **语义层级与计算阶段分离。** value、type、kind 可以分别由 regions 承载，并按阶段规则共同参与一次运行时集成。
5. **结构化存取与源码可读性兼得。** DBMR 不是不可理解的二进制黑箱；文本与 IDE 是语义图的一等交互界面。
6. **编辑也是受检查的语义操作。** 人类和智能体使用同一套身份、版本、校验和发布规则，不靠任意改写持久内存来维护程序。

## 2. 统一表示与职责分层

regional 是不同语义对象的共同物理承载机制，不意味着取消它们之间的类型、阶段、权限或生命周期边界。

| 层次 | 职责 |
| --- | --- |
| Regional 存储底座 | 区域分配、区域内引用、跨区域解析、生命周期和低开销对象访问。 |
| DBMR 持久语义单元 | 保存可重新加载的结构化语义图及解释它所需的身份、版本和依赖信息。 |
| Ontology 与类型核心 | 表达领域概念、关系、类型、kind、约束及可检查的组合依据。 |
| 业务程序表示 | 用 GADT 图表达纯计算、控制关系、数据依赖和抽象 effect 请求。 |
| 集成与执行运行时 | 加载多 domain、多层级 regions，建立集成上下文，维护执行实例与能力绑定。 |
| Effects 与 LLVM | 为抽象操作提供环境相关解释，实现原生执行，并在适当边界进行按需编译和特化。 |
| 源码与编辑工具 | 将语义图呈现为文本，提供 IDE 导航、诊断、结构化修改和版本审阅。 |

规范对象是有类型的语义图。DBMR 是它的高效持久表示，文本是它的源码表示，机器码是特定解释与环境下的执行产物。三者有不同用途，但不能形成彼此失去同步的多份语义真相。

## 3. Regional GADT：数据库、ontology 与待办程序

### 3.1 同一表示体系中的三类内容

图既保存“领域如何描述世界”，也保存“领域当前知道什么”，还保存“在什么条件下准备做什么”。ontology 不是仅供说明的字符串标签，业务程序也不是附着在数据库之外的一段不透明代码。

类型索引与构造子约束应使合法的业务程序连接能够被检查。领域关系还需要明确身份、含义、适用上下文和必要约束；结构相似或宿主语言类型相同，不足以证明两个 domain 的概念等价。

类型关系、领域映射和业务程序应能被内省。例如，工具应能回答某个待办引用了哪些领域概念、声明需要哪些 effects、哪些程序依赖某个类型版本，以及当前集成采用了哪条映射。静态分析无法确定的动态依赖应明确表示为未知或保守近似。

### 3.2 程序、执行实例与环境分离

概念上区分：

```text
P      = 业务程序图
S      = 某次运行的状态
I      = 领域映射、版本视图与绑定构成的集成上下文
H      = 当前上下文提供的 effects 解释

execute(P, S, I, H)
```

P 保存业务意图；S 保存已经计算出的值、当前执行位置、续延和等待状态；I、H 记录本次怎样理解领域连接并执行操作。多个执行实例可以共享同一份 P，而不共享进度或外部操作身份。

“不改写业务程序”指环境适配和执行不得隐式改变 P 的语义。用户有意修改业务逻辑时，可以通过编辑协议发布 P 的新版本；已经运行的实例依赖哪个版本必须明确。

### 3.3 图共享不等于执行共享

必须区分程序节点身份、领域实体身份、动态执行实例身份和某次 effect 发生的身份。两个位置引用同一个操作描述，不自动意味着该操作只能执行一次；恢复同一次外部操作，也不应无条件生成新的业务动作。

共享、循环、绑定作用域和执行顺序属于图的语义，不得在导出文本、编辑、优化或重新加载时被意外改变。

## 4. 多 domain、多 region 的即时集成

### 4.1 三种边界

region 是存储与生命周期边界；domain 是语义与治理边界；运行时进程是本次共同执行的边界。三者不要求一一对应。

一个 domain 可以有模型定义、领域事实、历史版本和执行实例等多个 regions。一个进程可以同时加载不同 domain 的 regions，也可以加载同一 domain 的不同版本或不同解释世界。多 region 是核心能力，不是单区域数据库完成后的附加功能。

### 4.2 集成上下文

即时集成应分别完成语义连接、行为连接和原生执行连接：先检查概念与类型如何对应，再确定 effects 如何解释，最后生成或选择适用的原生实现。

领域映射与组合规则本身应能够用 regional 图表达。推荐允许独立的集成 region 保存本次采用的映射、转换、能力组合及其来源，而不要求各 domain 修改自己的原始定义，也不要求所有 domain 服从一个预先固定的全局 ontology。

例如，订单域中的商品与库存域中的 SKU 可以通过上下文中的映射连接；这种对应可能需要转换、约束或额外计算，不应被默认为全局类型等价。即时集成不是自动猜出缺失的业务知识，而是使显式的集成知识能够晚绑定、被检查和被执行。

### 4.3 跨 region 引用与能力

持久引用的身份、运行时解析出的地址和领域实体身份必须分开。跨 region 引用应能在各 region 独立加载、重映射和版本选择后重新建立，不把某个进程中的裸地址当作长期身份。

引用能解地址，不代表语义上兼容或拥有操作权限。绑定时应检查目标身份、版本、类型或角色、映射依据及授予的能力。热路径可以使用经验证且生命周期已固定的地址，不要求每次字段访问都重新进行领域解析。

卸载、重映射、版本切换和原生代码替换必须遵循绑定依赖与生命周期规则。regions 同处一个进程不自动提供对任意原生代码的安全隔离。

## 5. Kind、type、value regions 与阶段化计算

### 5.1 语义层级

至少需要能够表达下列层级；物理表示不应把层级数量固定为三个。

| 层级 | 典型内容 | 主要作用 |
| --- | --- | --- |
| Kind-level | kind 表达式、类型构造子参数分类、类型形成约束。 | 支持类型展开、kind 推断和类型形成检查。 |
| Type-level | 领域类型、类型应用、GADT 构造子签名、effect 签名及相关约束。 | 支持程序检查、集成验证和编译。 |
| Value-level | 领域实体、事实、具体业务程序图、执行状态。 | 支持查询、计算与业务执行。 |

例如，以下仅为说明层级关系的伪记号：

```text
Prog     : EffectRow -> Type -> Type
OrderFx  : EffectRow
Receipt  : Type
checkout : Prog OrderFx Receipt
```

业务语言中的类型，在操作类型图的元程序中可以有值层面的表示。统一存储不等于把“一个类型”与“表示该类型的对象”混成同一逻辑概念，也不自动允许不受约束的自分类。

### 5.2 阶段不是进程的唯一全局属性

编译阶段可以计算普通值；运行时也可以保留或加载类型和 kind。正在运行的进程为新 domain 检查类型并生成代码时，相对于宿主是运行时，相对于新组合又是检查与编译阶段。

因此，语义层级、计算阶段、domain 归属和生命周期应分别描述。跨阶段可见性、引用、构造和执行权限必须有明确规则。kind 层级、universe 层级与阶段编号不能用一个整数概念替代。

### 5.3 已发布语义与求解工作区

应区分可变的解析／求解工作区和已检查、可被依赖的类型及 kind 图。未解约束、临时假设和搜索状态不应成为持久业务程序未经说明的依赖。

业务图不变还意味着它依赖的类型解释、映射和 effect 契约不能在原身份下悄悄改变。跨层引用必须具有稳定依赖与版本规则；不需要的检查中间状态可以释放，解释持久程序所需的定义则应可保持或重新加载。

### 5.4 元程序与可信检查核心

类型构造、解析、领域集成和 lowering 可以逐步成为操作 regional 图的程序。允许开放的构造与搜索机制，但接受结果的规则必须有可信检查边界，不能仅通过更换 handler 就宣布任意类型等价成立。

各 domain 应能够提供可加载的签名与定义，而不是必须把全部领域构造子预编译进宿主的固定枚举。具体元语言、检查证据与扩展机制另行规范。

## 6. Effects 解释与 LLVM 原生执行

### 6.1 业务程序声明意图，handler 提供解释

业务 GADT 表达抽象操作、返回类型、后续计算和业务约束；handler 实现操作在某个环境中的含义。真实执行、仿真、测试、重放或不同部署环境可以提供不同解释，但必须明确各自的契约和差异。

同一进程中的不同执行上下文可以采用不同 handler。不得依赖无上下文的全局注册或加载顺序，悄悄把一个业务请求派发到另一个 domain 或另一个仿真世界。

handler 可以把业务 effects 解释为较低层的 effects，再由环境实现最终处理。类型签名兼容是必要条件，不代表原子性、错误、顺序和恢复等行为承诺自动兼容；缺少能力时应明确拒绝或采用显式认可的解释。

### 6.2 续延与持久执行边界

当业务计算需要挂起或保存时，剩余计算必须能由程序节点、值环境、续延和必要作用域信息表达，而不是只存在于宿主 lambda、函数地址或原生栈帧中。

原生代码可以在一次执行片段内部使用寄存器和普通调用栈；只需在需要保存、挂起或交接的语义边界物化必要状态。文件描述符、连接和设备句柄属于运行环境，必须通过显式恢复或重绑定协议处理。

续延采用一次性还是多次恢复、深还是浅的 handler，以及如何处理取消、异常和资源所有权，均需专门规定。持久续延不自动保证外部 effects 的恰好一次执行；能在不同环境启动同一个程序，也不自动保证运行到任意位置都能切换环境继续。

### 6.3 原生实现与特化

LLVM 用于实现原生 handler、执行机制和必要的按需编译。可以先由原生运行机消费 GADT，再对稳定的程序、映射和 handler 组合做特化；不要求每张业务图必须先生成独立可执行文件。

机器码是特定语义版本、绑定和目标环境下的派生产物，不能取代业务图成为唯一程序本体。优化必须保留所选解释的可观察行为，不因共享节点、纯计算缓存或特化而擅自删除、重排或执行 effects。

语义上的即时集成与机器码 JIT 是不同层次。具体采用 AOT、JIT 或两者结合，不应改变业务程序的表达与集成契约。

## 7. DBMR：高度结构化的持久语义单元

DBMR 的目标不是保存任意进程内存快照，也不只是作为编译缓存。它应保存具有可识别结构和依赖的语义单元，使加载后的访问不以整图文本解析和重建为必经前提。

DBMR 应能够关联其语义根、身份、模型与格式版本、跨 region 依赖、所属领域和必要的层级信息。哪些信息在文件头、图内、侧索引或清单中表示，由存储规范决定；本文不固定文件与逻辑单元之间的物理对应方式。

### 7.1 可解释、可验证、可演进

加载时应验证格式、范围、布局、根类型及必要的引用和依赖条件。不兼容应被明确报告，不通过静默重建或清空文件来解决。语义层的类型检查不能只依赖最初在某次宿主编译中通过模板检查；导入、修改和重新加载也有自己的检查边界。

类型身份、schema 版本、布局兼容性和目标 ABI 应分别处理。同一语义单元能在不同环境使用，不意味着所有架构都能直接共享完全相同的内存镜像。布局变化、压缩、迁移和再物化需要显式协议。

整区重映射无需逐个修复区域内引用的目标，不能被扩大为任意对象搬迁、持久化刷盘、查询、跨域解析或垃圾回收都没有成本。性能应以真实加载、访问、集成和编辑路径测量。

### 7.2 数据库一致性与恢复

结构化图更新、并发读写、跨 region 可见性和异常退出后的状态必须有明确契约。第一阶段可以采用保守模型，但不得把 mmap 可写或正常退出后的刷盘等同于事务与崩溃恢复。

业务执行失败、语义编辑失败与持久提交失败是不同事件。提交前可回退的编辑不意味着已经发生的外部 effects 可以回滚。执行实例应明确依赖哪个程序版本、领域视图和集成版本。

存储应有容量、废弃状态和回收策略。数据版本变化与类型／布局变化应分别驱动查询缓存和编译产物的失效；只有被特化实际采用的事实与假设，才应进入相应的代码依赖。

## 8. 文本源码：快速、可读、可往返的语义投影

### 8.1 人类不应被迫阅读内存转储

DBMR 必须配套快速转为文本源码的工具。输出应表达领域名称、类型、构造子、绑定、关系和业务逻辑，而不是仅输出地址、偏移、内部 tag 或机器生成字段列表。

文本是可独立使用的一等界面，不以安装特定 IDE 为阅读前提。IDE 应能按 region、定义、节点、查询结果或选定子图即时呈现文本；大图采用按需展开、分页、流式或增量投影，不要求每次查看先遍历和输出整个数据库。

“快速”必须有边界：完整导出需要处理相应的完整内容；局部浏览应主要随可见范围和实际依赖增长。工具应保留名称、注释、文档与必要的来源信息，而不是把它们当作可以随物化丢弃的装饰。

### 8.2 可读视图与完整交换形式

应区分面向阅读的投影与用于完整重建的源码形式。阅读视图可以折叠、筛选或省略无关细节，但必须标明省略与所依赖的上下文，不能伪装为完整可重建输入。

完整形式必须明确表达共享、循环、绑定作用域、类型／kind 依赖和跨 region 导入。不能为了看起来像树状源码而复制共享节点，或把循环展开成无限文本。

通过稳定的节点／定义身份与源码位置映射，工具应能够在图和文本之间定位同一对象。具体采用可见锚点、限定名称或配套映射信息另行决定；不能把易变化的绝对地址作为源码身份。

基本往返目标是：

```text
load_text(render_complete(G), pinned_dependencies) ≃ G
```

这里的等价要求保留规定的语义、共享与绑定关系、必要身份及依赖，不要求字节布局、分配顺序或物理地址相同。只改排版或不影响语义的注释，不应意外创造新的业务实体或改变 effects 行为。

### 8.3 文本编辑也是正式入口

人类可以直接编辑源码；习惯文本 patch 的智能体也不应被排除。文本修改应经过解析、名称解析、kind/type/effect 检查和依赖验证，再成为语义变更，而不是直接覆盖活动 DBMR。

输出应支持稳定格式与低噪声 diff。对并行修改，优先按定义、身份和语义操作识别冲突，而不是把无冲突的文本合并误当成语义上必然正确。

源码投影本身不得执行业务 effects。读取敏感或无权限内容时应遵守可见性规则，明确标识删节；删节结果不能被当作完整备份或静默写回。

## 9. IDE：同一语义服务的交互界面

IDE 不应另造一套与运行时分离的模型。源码投影、语言服务、结构化编辑和运行时内省应共享身份与检查结果。

核心体验应覆盖：从值或业务程序跳转到类型与 kind 定义；跨 region、跨 domain 查找引用与映射；查看 effects 需求与本次 handler 绑定；查看某个诊断对应的节点、源码范围、依赖版本和失败原因。

编辑器应支持类型与上下文驱动的补全、局部重构、变更预览和影响分析。执行实例的状态、等待中的操作和诊断可以关联回原业务图，同时明确区分程序定义与运行状态。

局部编辑应触发有依赖依据的增量检查和视图更新，不以每次重建全部 regions 或重新自举 LLVM 为正常工作流。LSP、插件界面等具体承载协议不是本纲领预先固定的选择。

## 10. 智能体顺手的语义编辑机制

### 10.1 编辑结构，而不猜测字节或行号

智能体应能够按领域概念、类型、定义身份、引用关系和局部子图检索内容，读取足以完成任务的上下文，并获得当前版本、可用操作与约束。无需把整个 DBMR 转成文本塞入上下文，也无需自行维护偏移和对象布局。

结构化编辑应覆盖插入合法构造子、替换子图、修改字段或关系、重命名定义并更新引用、增加领域映射，以及调整 effects 绑定等操作。修改类型、kind 或 ontology 时，应显示受影响的程序、映射和执行依赖。

语义 patch 是正式入口，文本 patch 是同样受支持的入口。二者最终进入同一变更与校验机制，不形成两套不同的正确性标准。

### 10.2 最小编辑契约

建议的工作流是：

```text
读取选定语义对象与基准版本
    -> 构造局部变更
    -> 在隔离草稿中预览源码与语义差异
    -> 校验结构、引用、kind、type、effects、领域约束和权限
    -> 检查版本前置条件与提交冲突
    -> 发布新的语义版本并返回变更记录
```

一次编辑请求应明确作用范围、目标身份、基准 revision、操作集合和必要前置条件。重试应能够通过请求身份避免重复应用修改；这与业务 effects 的幂等性是两个不同协议。

检查失败或版本冲突应返回结构化诊断、受影响节点和可恢复草稿，不留下部分发布的无效图，不盲目覆盖别人已经提交的修改。可回退的发布与崩溃恢复保证应由明确的存储协议实现，而不是仅通过 API 名称宣称原子性。

对跨 region 变更，协议必须说明提交边界；尚不支持联合提交时，应拒绝或拆成具有明确阶段的工作流，不能悄悄留下半完成的领域集成。

### 10.3 权限、审阅与执行分离

“能编辑程序”不自动授予“能运行程序”，也不自动授予读取所有 domain 的能力。默认的预览和校验不执行真实业务 effects；确需外部输入的检查必须声明所用能力并记录依赖。

人类应能阅读同一变更的源码 diff、语义摘要和影响范围。智能体应能获得机器可读的诊断和提交结果。结构化协议不预设特定智能体、厂商或传输方式，也不要求智能体绕开 IDE 与人类使用的检查核心。

## 11. 版本控制、源码与持久表示的协作

语义图、文本源码和 DBMR 应通过明确的导出、导入、编辑与发布流程保持一致，不能独立修改后依赖猜测来合并。源码视图应携带足够的基准版本信息，编辑结果要能准确应用到所针对的语义版本。

版本控制应能保存和审阅语义单元的定义、必要依赖、领域映射、handler 契约与物化条件。Git 可以管理稳定源码投影及清单；大型领域数据、运行实例、二进制镜像和派生代码如何存储与分发，应按用途另外规范，不能默认全部提交到源码仓库。

语义身份与源码位置、文件路径、物理偏移必须解耦。可重复构建的目标首先是从锁定输入重建相同的已检查语义及适用执行产物，不把字节完全相同的内存布局作为默认前提。

持久语义单元不是可随意删除的缓存。派生索引和机器码可以按声明的规则重建；业务事实、程序意图及人工注释的删除或迁移必须是明确的用户操作。

## 12. 端到端验证目标与推进顺序

优先证明共同语义链路，而不是分别扩展互不连接的组件。最小样例应覆盖两个独立 domain、一个显式集成上下文、一份不因环境改变而改写的业务 GADT，以及两种 effects 解释。

| 阶段 | 主要交付 | 必须观察到的结果 |
| --- | --- | --- |
| 语义核心 | 小型 kind/type/program 表示、领域签名、检查器与参考解释。 | 非法类型连接被拒绝；effect 的结果能决定后续业务分支；业务逻辑不藏在不可持久化的宿主回调中。 |
| 多域与持久化 | 多 regions、跨域映射、DBMR 身份与版本、独立执行实例。 | 同一进程加载独立领域并完成检查；重新加载后图的身份、共享和依赖仍成立；不兼容输入被拒绝。 |
| 源码与编辑闭环 | 完整文本往返、局部投影、IDE 导航、文本和结构化 patch。 | 人类可阅读和修改；智能体可定位并验证局部变更；失败和冲突不破坏已发布语义。 |
| 原生执行 | LLVM 原生 handler／执行机制、必要的特化与增量绑定。 | 同一业务图在受控真实环境与仿真环境下按各自契约执行；原生结果与参考解释一致。 |

一个贯穿样例可以采用订单域与库存域：分别定义概念与数据，通过集成图连接商品和 SKU，执行“查询后根据结果分支”的业务程序。替换库存实现或改用仿真 handler 时，只调整集成与绑定，不修改业务图。

样例还应验证：运行时加载领域签名并进行 kind/type 检查；缺少能力时拒绝执行；导出包含共享和跨域引用的源码并重建等价图；通过智能体 patch 修改映射并预览影响；以同一基准版本制造编辑冲突，确认不会静默覆盖。

性能测量分别覆盖加载与验证、冷热查询、跨域绑定、原生分派、局部源码投影、局部检查、编辑发布和恢复。先确定正确性与依赖边界，再优化可见路径；不以 REPL 响应时间或功能数量替代整个系统的验证。

## 13. 不应混淆的承诺

统一 regional 表示不意味着 value、type、kind 的逻辑规则相同；图可达不意味着领域兼容；类型兼容不意味着拥有执行权限；共享映射不意味着事务；单进程不意味着安全沙箱；持久程序不意味着外部 effects 可以自动回滚。

本项目不以成为通用 C++ REPL 为最终目标，不以中央通用 ontology 取代所有领域模型，不以自由文本标签取代类型与关系检查，也不要求人类或智能体直接修改二进制布局。

本纲领不承诺自动推导缺失的业务映射、任意跨架构二进制兼容、任意时刻迁移执行、无限制 ontology 推理或立即具备完整分布式数据库能力。这些能力只有在其语义、边界和实现经过单独设计后才可宣称。

## 14. 需要后续规范的关键决策

| 议题 | 待确定内容 |
| --- | --- |
| 类型与 kind 核心 | GADT 索引、类型等价、kind 推断、依赖类型与 universe 范围、动态签名的可信检查。 |
| Ontology 语义 | 身份与等价、关系约束、开放／封闭世界选择、推理范围、映射依据与领域治理。 |
| 引用与版本 | 跨 region 对象定位、代际与版本、卸载固定、迁移、压缩及引用失效规则。 |

| 持久一致性 | 单 region 与跨 region 提交、读视图、故障模型、恢复和历史保留。 |
