## Before coding

Start with the intended idiomatic source and the real acceptance workload. Include the smallest coherent seed increment needed to express that source under confirmed language contracts. Use the intended source for delivery and keep temporary substitutes isolated. Send the proposed structure to the CoD design discussion and obtain explicit clearance for the identified batch before writing new code. Include tests, scripts, native glue, tooling and new code inside existing files. State which caller enters the operation, who owns its state, how results cross the boundary and what happens on failure. Group related changes that can be reviewed together. Work within a cleared proposal can proceed as one batch. Return to review before expanding it. An existing implementation, language qualification or retrospective disposition does not preapprove later additions. The design discussion settles questions within the user's principles and brings material trade-offs to the user.

## Scoped new-code clearances

- **Booter module graph architecture r1.** The [reviewed design](../applications/cod-booter/docs/ModuleGraph.md) covers compiler and service responsibilities, graph and frame lifetimes, and acceptance. Mainline submits the structure of concrete code batches against it.
- **Seed nominal sum declaration parser r1.** Cleared for the seed syntax parser, the registrar's located unsupported-form rejection, and their direct probes. Use an explicit nominal sum discriminator and a typed list of constructor alternatives. Share the existing record field parser and preserve each alternative's identity, span, field mode and target access. A fieldless alternative is valid; an empty alternative list is malformed. Branch on the explicit sum discriminator before product registration. Verify ordinary product and C-record behavior, export, malformed declarations and rejection before output. Checked sum layout, construction, matching, indexed storage, booter parsing and lowering need their own code proposals.
- **First executable seed sum r1.** The syntax, checked program, checker and LLVM emitter may implement cross-module nominal dctor selection, fresh lexical construction of direct bits fields and constructor-pattern reception. The checked representation owns sum/dctor identity, field schema, owner, initialization and match evidence. LLVM computes discriminant storage, maximum payload alignment and size for the selected target. Check a fieldless and differently aligned alternative, matching before projection, partial initialization, ordinary visibility and case coverage in both native modes. Production AST arrays, non-bits payloads, foreign layout and constructor overload execution retain separate review scopes.
- **First indexed booter AST path.** Cleared for the [private initialized slot array](../applications/cod-booter/docs/ModuleGraph.md#first-indexed-ast-path), the actual literal/call/return producer, enclosing syntax, binding, checking and native command consumer, and their direct fixtures. The seed checker, checked program and emitter may implement the named-array length/fill, aggregate field placement, indexing and valid bits transfer required by these concrete layouts. Reuse existing syntax, nominal and owner evidence and allocation services. The distinct storage owner and source revision, successful-only publication, payload projection and real emitted result are acceptance obligations. No general resizable collection, uninitialized-array form or native AST ABI is implied. Other alternatives and broader production migrations require scoped structural review.
- **AST node identity in the booter.** Cleared for graph-local key issuance on source open, frame and table state, parser construction of bits IDs, lookup by the checker and lowering, and focused isolation probes. The [frame and node identity contract](../applications/cod-booter/docs/ModuleGraph.md#frame-and-node-identity) specifies ownership, failure and acceptance for both the isolated route and its production interfaces.
- **Single-file typed booter object route.** Cleared for the actual CompilerCLI, CoD frame activation, existing compiler stages, generated host entry, existing provider implementations and the direct file-to-object acceptance in an isolated build. The [single-file contract](../applications/cod-booter/docs/ModuleGraph.md#single-file-object-route) specifies buffer owners, status translation and the distinction from final graph publication. Production build configuration retains its separate authorization.
- **Existing booter syntax producers and consumers.** The [module inventory and acceptance](../applications/cod-booter/docs/ModuleGraph.md#typed-syntax-consumers) cover the isolated direct migration by syntax family, required CoD caller signatures and focused regressions. Each pass keeps its current semantic checks. New grammar, changes to native contracts and the graph traversal cutover have independent review scopes.

### Lexical backing for the indexed AST array

For the [initialized slot array](../applications/cod-booter/docs/ModuleGraph.md#first-indexed-ast-path), generated code may request an aligned byte extent through one private operation in [the shared runtime header](../cod/runtime/cod_lang_runtime.h) and [its C implementation](../cod/runtime/cod_lang_runtime.c). The caller supplies the cleanup-list address of the actual lexical owner selected for placement, the checked byte size and the element alignment for the compilation target. A nested caller allocating in an outer lexical owner must supply the outer list. Named-region placement follows its own allocation path.

Use the existing [raw storage service](../include/cod_region_storage.h) and lexical list's release callback. Check representability before narrowing, and honor the service's power-of-two alignment limit through `max_align_t` on the executing target. Lowering must diagnose an unsupported element layout before emitting this call. For zero logical bytes the service can use minimum backing. Acquire the cleanup record and backing before linking either into the list. On acquisition failure, release any partial acquisition and leave the list as it was. On success, the registered callback releases the backing and cleanup record exactly once during owner teardown, after its deferred actions finish.

The seed keeps length and fill evaluation, layout, typed stores and publication under the existing array contract. Successful acquisition gives the lexical owner responsibility for the backing even if a subsequent initialization or table replacement fails. Readers retain the preceding published table until a complete replacement is installed. Verify zero length with an observable fill, aligned slots, partial acquisition failure, and a deferred read of the previous table after failed growth. Verify that an outer-owned extent survives inner teardown and releases once on exit, alongside existing text or builder allocations. These checks supplement the real parser-to-object acceptance.
