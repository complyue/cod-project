## Design review and delivery responsibilities

The design discussion maintains the language contracts and confirms major choices about program structure and algorithms before mainline implements them. Examples include splitting a compiler into passes, changing how an inference solver computes its result, and choosing how modules can run concurrently. An unchanged source contract can still admit several substantially different algorithms. Bring the choice while the alternatives are open. The design discussion takes a language or value trade-off outside its delegated authority to the project user.

Development mainline implements, verifies and publishes within the agreed design. It chooses data members, helpers, patch boundaries, test fixtures and release evidence. For example, applying an already approved ownership model to another private effect record is a mainline decision. Replacing the ownership model across compiler phases calls for design confirmation. A review covers the decision through delivery. Mainline returns if a major choice changes or a confirmed guarantee cannot be met, and reports material milestones or blockers when useful.

For example, if the user asks whether a redesigned AST is in production, the design discussion can inspect the public commit and ask what the production driver still needs. If the supplied results cover object emission but omit provider generation, the reviewer identifies the missing comparison and asks mainline for its result. Mainline owns the comparison, repair and implementation push. The reviewer reports the outcome or the outstanding blocker to the user.

## Before coding

Start with the intended idiomatic source and the real acceptance workload. Include the smallest coherent seed increment needed to express it and keep temporary substitutes isolated. If the work introduces a major structural or algorithmic choice, identify its real caller, state ownership, effects on failure and the trade-off that needs confirmation. ### Justifying compiler work before coding

The project user permits retiring the entire existing set of test fixtures. A batch may remove positive and negative cases together with their dedicated execution entries. Add a case back when a specific implementation or delivery question needs it. A production input or an existing receipt can already answer that question. Previous lists of fixtures record available evidence and confer no standing maintenance or replay requirement.

Identify the source case and the decision that depends on the proposed work. A summary copied into a second table has an intermediate reader. Follow it to the operation that would emit different code, accept or reject a program differently, lose a required diagnostic, or violate another qualified contract. For an added regression gate, identify the regression it would catch and whether existing acceptance already catches it. Use the source, contract and existing evidence when they settle the question.

Consider what the consumer can do with a cheaper sound fact. For example, a possible write through an alias can invalidate an earlier nonnull proof. A later use can check the current target. If that satisfies the component’s contract on the actual workload, use that approach. If a promised initialization or a use after cleanup requires stronger evidence, identify the path and destination that require it, then limit collection, storage and verification accordingly. Keep soundness, ownership, cleanup, required diagnostics and supported valid inputs in the comparison. Omit the proposal or its unsupported precision when review finds no decision that needs it. A change to a qualified obligation still follows the existing design process.

For the [ordinary reference example](#consuming-completed-callee-behavior), the emitter must preserve both the store and its order relative to failure. Running the handler can test that order. A static per-exit write history needs a separate caller decision that consumes it. An `init` parameter requires proof that its promised write occurred on every successful completion. A definite-write fact for the selected destination can satisfy that obligation.

### Producing effects during final body validation

A seed body’s outgoing `CallEffects` describes what a call can do on each completion. During final body validation, the seed prepares possible targets, settles loop headers and then checks the body using those results. Only the last traversal produces the outgoing summary used for comparison. Each earlier traversal still performs the local work its successors depend on, including preparing owners and operands, routing exits through handlers and cleanup, and discovering callable instances. For example, a symbol requirement belonging to a queued cleanup must survive even when this traversal has no outgoing summary to fill.

The choice depends on who consumes the result. In ordinary effect closure, the iteration that settles a loop can itself supply the summary consumed by the solver. It retains that responsibility. Final validation keeps the comparison for each existing binding interpretation, the separate completed scalar and leaf paths, emitted frame data and warnings. Its instance walk covers methods discovered during materialization. The module entry retains its existing checking path. The broader migration of the legacy solver remains open.

Acceptance uses the seed’s translation of `ModuleIndex`, `ProviderNames` and `NativeSource` with matching LLVM IR, bitcode and provider files. The focused inputs distinguish a borrowed write in a loop with failure and cleanup, a returned callable whose validity depends on a condition, and the warning for nonvoid fallthrough. Mainline owns verification and publication.

### Restarting a pass from entry

In the C++ seed, `read_effects` subscribes a caller instance to its callee. When the callee’s summary changes, `close_effects` can enqueue that caller and `check_instance` reconstructs its frame from entry. An ignored Boolean result in one conditional arm can thereby cause another walk over the prefix, the sibling arm and a suffix whose incoming facts all stayed the same. The source of that repeated work is the choice of dependency granularity.

For a new design, identify what each pass establishes and when its result is fit for consumption. The counterexample begins when a caller takes a provisional callee summary as input. Narrowing a later wakeup to one branch still leaves that dependency in place. During extraction a caller can record the call and continue reading its own source. The collector can forward a newly discovered callee requirement along recorded call edges. Only the later checking phase can use the completed behavior to discharge obligations at that call. A separate final pass can check the whole solved result before publication.
