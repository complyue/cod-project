### Registering a variadic method family

Apply D-10's [standalone-method rule](SymbolicDynamicScope.md#runtime-array-expansion-and-one-variadic-parameter) to each actual family as it forms. In the seed, reuse local method registration and the composed receiver view. In the CoD booter, parse the exact final ordinary-formal suffix `...` with its span, retain that fact in the typed formal, and use it in local registration and checked module selection. Verify that `.`, `..` and other operator tokens retain their respective boundaries.

Track bodyless promises separately. Count distinct defining methods in the selected interpretation. Preserve existing conflicts between incompatible interpretations of one definition. Independent source-preserving views remain separate. A previously proved source interface can carry the defining module, method identity, implementation presence and variadic fact through re-export. Validate identities and graph row bounds before using them. A native body ordinal is unnecessary to check family membership.

Report an unused local conflict at the declaration and an imported conflict at the combining directive. Preserve structural evidence from dependencies long enough to check the receiving composition. A valid standalone method can still encounter a located execution-profile stop. Do not publish executable coverage from structural evidence. Existing syntax, body checks, callable promises and fixed-only overload checks apply in their respective phases.

Verify both registration orders, disjoint domains, differing prefixes, same-method diamonds, independent source views and authorized imported extensions in both frontends. Check the fixed implementation under a bodyless variadic promise and preserve its cleanup. Compare the normal compiler commands, earlier artifacts after rejection, and the supported command baseline. This clearance covers registration and checked interfaces. Execution of one or several expansions needs its own implementation review.

## Design review and delivery responsibilities

The design discussion interprets confirmed semantics, reviews the structure of each proposed code batch, and publishes the scoped design decision and acceptance criteria. It can examine source, diffs and existing verification records to assess a claim. When a change would weaken a confirmed guarantee or requires a material choice outside its delegated scope, it takes that choice to the project user.

Development mainline owns the implementation from correction through production cutover. It identifies the affected commands, establishes what the previous version accepted, runs the compatibility checks against the exact candidate, fixes regressions and publishes the first checkpoint that preserves the required behavior. Mainline makes that delivery decision within the cleared scope. Fresh design review applies when the proposed architecture or contract changes.

For example, if the user asks whether a redesigned AST is in production, the design discussion can inspect the public commit and ask what the production driver still needs. If the supplied results cover object emission but omit provider generation, the reviewer identifies the missing comparison and asks mainline for its result. Mainline owns the comparison, repair and implementation push. The reviewer reports the outcome or the outstanding blocker to the user.

## Before coding

Start with the intended idiomatic source and the real acceptance workload. Include the smallest coherent seed increment needed to express that source under confirmed language contracts. Use the intended source for delivery and keep temporary substitutes isolated. Send the proposed structure to the CoD design discussion and obtain explicit clearance for the identified batch before writing new code. Include tests, scripts, native glue, tooling and new code inside existing files. State which caller enters the operation, who owns its state, how results cross the boundary and what happens on failure. Group related changes that can be reviewed together. Work within a cleared proposal can proceed as one batch. Return to review before expanding it. An existing implementation, language qualification or retrospective disposition does not preapprove later additions. The design discussion settles questions within the user's principles and brings material trade-offs to the user.
