## Design review and delivery responsibilities

The design discussion maintains the language contracts and confirms major choices about program structure and algorithms before mainline implements them. Examples include splitting a compiler into passes, changing how an inference solver computes its result, and choosing how modules can run concurrently. An unchanged source contract can still admit several substantially different algorithms. Bring the choice while the alternatives are open. The design discussion takes a language or value trade-off outside its delegated authority to the project user.

Development mainline implements, verifies and publishes within the agreed design. It chooses data members, helpers, patch boundaries, test fixtures and release evidence. For example, applying an already approved ownership model to another private effect record is a mainline decision. Replacing the ownership model across compiler phases calls for design confirmation. A review covers the decision through delivery. Mainline returns if a major choice changes or a confirmed guarantee cannot be met, and reports material milestones or blockers when useful.

For example, if the user asks whether a redesigned AST is in production, the design discussion can inspect the public commit and ask what the production driver still needs. If the supplied results cover object emission but omit provider generation, the reviewer identifies the missing comparison and asks mainline for its result. Mainline owns the comparison, repair and implementation push. The reviewer reports the outcome or the outstanding blocker to the user.

### Consuming completed callee behavior

**Collection and propagation.** Identify the selected callable instance and interpretation. Collect the input requirements and effects needed by a particular caller-side check, along with their call dependencies and source locations. Collection may propagate new information between pending records. For example, a borrowed-read requirement discovered in a helper can reach its callers’ pending requirements. Propagation does not decide whether an actual argument satisfies that requirement. A completed description can remain conditional on argument values, actual owners, aliasing and incoming bindings.

**Use.** The caller checker takes the completed behavior as read-only input. On a path where the arguments complete and the call is entered, apply that behavior to the actual places and state. Route operand failure before entry at the operand. For a normal successor or a handler, rely only on facts established on all paths reaching that point under its known conditions. Call-site results and diagnostics belong to this checking phase. An unavailable prerequisite leaves the dependent check pending or unproved. A consumer cannot fill a gap by changing a callee summary, assuming an empty effect, or retrying an arm on a producer notification.

**Writes through an ordinary `ref`.** A handler with a live reference to an already initialized scalar can read it after a call that may have changed its value. It reads the stored value without having to prove which write ran. For example, if a callee sets an initially false Boolean to true between two potentially failing indexed reads, the same bounds handler can observe either value. A checked exception declaration also gives no guarantee about preceding writes. If a caller previously proved a nullable field non-null, a call that might store null there through any alias invalidates that proof. The caller can test the field again. A use that depends on a stronger postcondition needs separate evidence. The [trusted seed](../applications/cod-booter/README.md#trusted-source-and-the-seed) preserves the order and visibility of writes and cleanup during emission.

**Writes promised by `init`.** The checker must prove the promised initialization of the selected destination on every successful completion, including its cleanup. A possible write cannot discharge that obligation. On an exceptional exit, completed writes remain visible and the call supplies no blanket initialization guarantee. A handler reading a previously uninitialized destination still needs definite initialization on every path that reaches the read.
