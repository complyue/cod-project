# Parser combinator lib support

Research WIP · revision 5 · 2026-11-28

Can a reusable grammar be ordinary CoD data, while an effectful call on each rule delivers one of Megaparsec's four outcomes to its caller? The first workload is an expression grammar whose next production depends on an operator it just read. The same grammar must parse two source files into independently owned syntax trees. A second workload recovers two malformed declarations and still parses the following statement.

## Packaged production parser

**`pcl.cod` is the parsing HLVM. The production CoD parser is one application of it.** The planned `e-wrks/cod` toolchain ships this parser combinator library together with `cod.grammar`, the application’s grammar program in DBMR format. On the compiler’s normal path, the application runs that program on `pcl.cod` with a CoD source file as input and the grammar image open read-only. The mapped grammar has actual owner `G`. Each parse obtains its input and dynamic bindings from its session and writes its AST under an output owner `N` distinct from `G`. The grammar image contains rule data and same-region edges. Callbacks, installed handlers and input-specific parse results belong to active runs. [Distribution decision](../CHANGELOG.md#h-production-parser-bundle-20261126) · [The CoD parser application](../papers/AlgebraicEffectsIsAllYouNeed.md#the-cod-parser-as-an-application-of-the-parsing-hlvm)

Run the nested-expression and malformed-declaration workloads below against that image. Observe their source spans, ASTs and diagnostics, then release one result and read the other. A fresh compatible process should reproduce the observations when the image maps at a different base address. Validate the format, root layout and required edges on the file actually opened. ## The rule interface

Use the release source of **Megaparsec 9.8.3** as the initial behavioral reference. Its rule receives an entry state and four continuations. Each continuation has the same answer type, chosen by the invoking context. A success supplies the semantic value, successor state and hints. A failure supplies a structured parse error and successor state. Consumption is a control decision made by the rule. An explicit parser-state update can change the offset and still select empty success. [Four-way interface](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L129-L141) · [State operations](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L632-L639)

| Callback | Payload | Meaning to the caller |
| --- | --- | --- |
| `cok` | value, state, hints | Success with consumption. A following empty failure in a sequence becomes a consumed failure. |
| `cerr` | error, state | Consumed failure. Ordinary ordered choice passes it out. |
| `eok` | value, state, hints | Empty success. It selects the left alternative just as firmly as consumed success. |
| `eerr` | error, state | Empty failure. Ordered choice may try its right operand from the saved entry state. |

Here is the research signature specialized to expressions. Type and parameter names are illustrative. `ParseState`, `Hints` and `ParseError` are views backed by live run storage. The driver makes the selected state current before handing control to a callback. A retained snapshot needs its own stable logical contents, even if the session mutates in place.

```cod
proc (const ExprRule in G).(())(
    here cok(value:const Expr in N, state:const ParseState in P, hints:const Hints in P) -> void,
    here cerr(error:const ParseError in P, state:const ParseState in P) -> void,
    here eok(value:const Expr in N, state:const ParseState in P, hints:const Hints in P) -> void,
    here eerr(error:const ParseError in P, state:const ParseState in P) -> void,
    session:ParseSession in P, out:AstArena in N
) -> void where {const owner G, owner P, owner N}
```

The explicit session and output formals exhibit the actual owner evidence. The runner can install the input, session operations and grammar environment as typed dynamic effects for named productions. Such a call uses the current run's bindings. A writable AST allocator must still have authority for the same actual `N` as the success payload. A callback's lexical activation is a further, separately bounded lifetime. An output node wanted after the call needs a live output owner. [Owner evidence in a callback and its ordinary inputs](ImplementationArchitecture.md#forwarding-the-graph-allocator-through-a-named-here-receiver) · [Invocation and dynamic bindings](CallableStorageAndHereAccess.md#an-effect-in-a-here-callback)

Normal completion of one rule invocation selects exactly one callback, once, as its terminal parser action. Call it with the branch's final state already established. An exception, protected transfer or resource failure during that callback propagates through ordinary cleanup. It cannot cause a second callback. CoD's general `here` supports repeated synchronous invocation and forwarding. The stronger completion law belongs to this library. Forwarding four named formals suffices for a transparent wrapper. A combinator can forward existing callbacks or supply an [inline here literal](SymbolicDynamicScope.md#inline-here-arguments) for any of the four outcomes. A trailing block supplies the first formal. [Nested and multiple callback formals](https://github.com/complyue/cod-project/blob/4a4df1338a893433d2e95512511495824f169380/design/ProducersAndTransformers.md#L295-L304) · [Trailing callbacks](SymbolicDynamicScope.md#trailing-callback-arguments)

The concrete `void` form lets the top-level callbacks deliver into caller-owned destinations. Upstream quantifies over an answer type independently of the rule's semantic value. Compare a scalar-answer and a borrowed-value driver with the `void` driver, including abrupt completion, before treating output slots as a general substitute. `Rule_G(A)` below abbreviates this protocol. It does not presume syntax for a generic ADT, a named parameterized signature, or higher-rank answer polymorphism. [Named signature research](../docs/DesignTopics.md) · [Upstream parser type](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L129-L141)

## Owners, checkpoints and publication

| Role | Lifetime and contents | Required evidence |
| --- | --- | --- |
| Grammar `G` | Reusable rule receivers, configuration, named recursive entries and same-owner child edges | Readonly while interpreting. Construction needs a writable capability for the actual destination. |
| Input `I` | Source bytes or a token stream with source spans | Lives through every read. An independently retained AST can copy spelling or record source identity and span, with explicit source access to resolve it later. |
| Run `P` | Current logical stream, offset, position state, delayed errors, branch checkpoints, diagnostics and transient hints | Each invocation or session owns its work. Reentry saves the actual outer activation. An error delivered after rewind must still be readable. |
| Result `N` | Published AST nodes and same-owner edges, including recovered syntax | **Actual `N` differs from actual `G`.** Results survive parser-frame cleanup and are usable as long as their output owner lives. |

Distinct binder names in a `where` clause do **not** prove that two actual owners differ. A first runner can construct a fresh output region while the grammar is live. An API accepting caller-supplied regions must establish the inequality, by construction or another supported proof. The general proof for arbitrary callers remains open. Input and run are separate roles; this WIP mandates actual inequality specifically between grammar and result. A regional AST must not contain ordinary cross-owner field references back into the grammar, session or source. A borrowed run diagnostic needs copying or an explicitly retained owner before publication. [Owner equality and regional edges](RegionalOwnership.md#pointer-variables-and-owner-generic-parameters)

A checkpoint must restore the logical input remainder, offset, position state and delayed-error collection. Grammar-table updates included in speculative parsing need a branch-local overlay or a documented commit point. Define which AST roots, diagnostic-list entries and semantic actions become visible on success. Restoring a dynamic binding restores the selection of its target. It does not undo writes already made to that target or external I/O. A first implementation may keep unpublished allocations until run teardown, roll back publication marks and restrict speculative actions to parser-managed effects. A reclaiming implementation owes the same visible behavior and must first prove all delivered values remain live. Two particular survivors are the original error returned by `try` and the successful AST returned by `lookAhead` after restoring the cursor. [Full parser and position state](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/State.hs#L38-L111)

## How the combinators route control

**Sequence and dependent rules.** When the first rule succeeds, invoke the next production with its value and successor state. A consumed first success promotes a following empty success/failure to consumed success/failure. An empty first success leaves the next rule's classification intact. Carry accumulated hints into the next rule's empty outcomes according to the reference. Forward a first failure immediately. Thus a length field may determine a `readExactly(n)` production on the same activation. A simple `map` adapts both success callbacks with the typed conversion and forwards both failure callbacks. A persistent conversion strategy can itself be rule data. [Upstream bind](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L223-L246)

**Ordered choice.** In `p <|> q`, give `p` the outer `cok`, `cerr` and `eok`. Replace only its `eerr`. That adapter saves the left error and failed state, restores entry state, then invokes `q`. Right consumed success goes straight out. Right empty success can inherit eligible expected-item hints from the left. If the right fails, combine the errors and separately select the failed state at the greater offset (right wins state ties). In 9.8.3 two empty trivial failures have a special case: when one error is at choice entry and the other is deeper, preserve the entry error. Other merges follow the error rules, including expected-set union at equal trivial offsets, preference for a fancy error over a trivial one at the same offset, and union of two fancy errors at the same offset. Only a trivial error at the current offset contributes expected-item hints. [Choice](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L351-L385) · [Error merge](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Error.hs#L213-L242) · [Hint conversion](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L648-L687)

For example, `(pure('x') <|> char('a')) *> char('b')` on `ab` fails at offset 0. The left rule already chose empty success, so failure of the downstream parser cannot reopen that choice. This example distinguishes terminal callbacks from catch-and-retry around the whole success continuation.

| Operation | Observable routing in the reference |
| --- | --- |
| `try p` | On either failure pass its original error to outer `eerr` with the entry state. Preserve each success. Error offset and state offset may now differ. |
| `lookAhead p` | On either success deliver its value via `eok` at entry, with empty hints. Pass both failures through, including consumed failure. |
| `notFollowedBy p` | Either success becomes an empty failure describing the entry token or EOF. Either failure becomes empty success at entry. |
| `label`, `hidden` | A label replaces the expected set on empty trivial failure and updates empty-success hints. Hidden strips the corresponding hints, including on consumed success. Preserve committed failure and custom/fancy errors. |
| `observing p` | Wrap success as a value. Convert each failure into a success carrying its error with the same consumption class and state. Empty failure can produce same-position hints. |
| `withRecovery recover p` | Start recovery at the failing state's position with the original error. On recovery failure reproduce the original error, state and failure class. On recovery success use its success class and state. Discard recovery hints. A consumed original failure followed by consumed recovery success gives empty hints. The other success cases derive hints from the original error at the recovery exit offset. |

[Labels, lookahead, recovery and observation](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec/Internal.hs#L422-L491)

**Diagnostics and runners.** Compare unexpected tokens, expected sets, labels, custom errors, hints and delayed errors as structured data before comparing rendered text. Finalize a run with a nonempty offset-ordered error bundle if delayed errors survive, even after a successful grammar exit. Preserve the initial position state for rendering. The CoD compiler may additionally retain a recovered syntax tree for tooling and must report failed compilation when the file contains errors. Exhausted workspace is an incomplete run; treating it as a recoverable grammar mismatch can select a different valid-looking program. [Reference runner](https://github.com/mrkkrp/megaparsec/blob/7a40f5d1b13ab4ff4736676566f6adf458aae8a4/Text/Megaparsec.hs#L279-L300) · [CoD recovery contract](../applications/cod-booter/README.md#whole-file-parser-recovery)

Four callbacks give a control interface. To claim full parser semantics, also compare token and auto-backtracking chunk primitives, empty/nonempty takes, EOF, source slices from `match`, get/update state, explicit replies from custom primitives, error registration, custom stream position traversal and bundle rendering. Exercise Unicode source positions, tabs, EOF and token streams whose token offsets differ from byte offsets. Derived repetition, separators and lexer helpers should be tested through productions using them. Record version-specific differences or intentional CoD extensions separately. The earlier roadmap cites 9.7.0, whose empty/empty merge differs on an example below. ## Reusable rules and the scope of language support

A concrete ADT may declare an effectful `.(())`, receive fresh callbacks for each call, and supply a synchronous compatible `here` argument. Different receiver layouts can implement the same success payload. For example, `integerExpr <|> nameAsExpr(identifier)` has two rules that produce an `Expr`. A direct `integerExpr <|> identifier` must be rejected when `identifier` produces a `Name` and there is no adapter. A single integer `RuleId` retains neither that result relationship nor the identity of its grammar table.

| Desired use | Candidate representation and question |
| --- | --- |
| Execute a user-defined rule now | A concrete ADT with `proc (const R in G).(())(...)`, prepared once and borrowed synchronously. Store configuration in the receiver. Keep the cursor, recursion frames, checkpoints and callbacks per invocation. |
| Give a selected effectful receiver a local name as a callable value or return it while its owner lives | A proposed bound `proc … in G` view would keep receiver identity, access, selected method family and actual owner. Each invocation supplies fresh callbacks and uses its current dynamic context. Existing functor values bind `func` only. Restricting the new value to initialized ADT receivers would preserve the exclusion of free-standing procedures, captured callbacks and extracted handlers. |
| Save a composite or finite recursive grammar in a region | Concrete typed child references or a named sum with same-owner edges can represent a closed grammar. Use a named nonterminal or validated reservation and initialization for a cycle. A parenthesized rule must consume the opening delimiter before recursive reentry. This supplies no general left-recursion algorithm. |
| Save two arbitrary third-party rule implementations in one reusable `Choice(A)` | Compare compiler specialization with an owner-relative data reference carrying checked invocation-protocol evidence. The two receiver types may differ, both must produce `A`. A lexical callable view or a previous `here` cannot serve as a regional field. Include a `map(Name → Expr)` node to expose the hidden intermediate type, and a second library-defined result type to test extensibility. |

Constructing `p <|> q` can allocate a grammar node while evaluating neither parser on input. The builder needs writable authority for the actual `G` of both children. A dynamically selected builder for another grammar must fail that test. The retained value cannot refer to an operator-local temporary. For a booter experiment, a fixed binary spelling with library overloads is a separate proposal. Its fixity, dispatch and executable scope need review. Bootstrap acceptance does not depend on user-defined fixity or migration of the booter grammar. The documented frontend probes still identify missing OO receiver and ordinary `here` execution paths. ### Lexical composition or an independently owned plan?

The design choice concerns **what the combination operator produces**. For a rule that must survive its builder or be opened from `cod.grammar`, investigate a regional ADT graph first. Its entry can accept the four fresh synchronous `here` arguments on every call. For a connection used only by live callers, the existing lexical representation has a different advantage: it can borrow actual targets from several owners and preserve their current state and control destinations. Neither choice requires first resolving the proposed bound `proc … in O` value type. [Lexical pipeline connections](ProducersAndTransformers.md#lexical-variables-for-open-pipelines) · [Callable storage rules](CallableViewsAndCaptures.md#callable-views-have-lexical-storage)

Take a price filter whose writable limit is initially 100. Compose it, change the original limit to 70, then offer a fare of 80. A `here` plan retaining that receiver reads 70 and rejects the fare. A regional constructor that copied 100 into the plan accepts it. A regional edge to the **same** live receiver inside the plan owner would see 70 as well. This example separates aliasing policy from storage duration. A library overload must specify whether an operand supplies configuration by value or a live node by reference. Receiving the result in a longer-lived variable cannot select a different policy. The existing `InvoiceRule` overload exhibits the snapshot option with two scalar fields. [Regional functor overload](ProducersAndTransformers.md#a-regional-functor-returned-by-an-overload)

**Owner granularity.** Use one independent owner for a complete plan, or for a component with an independently required lifetime. An in-memory plan already benefits from this lifetime boundary. DBMR publication adds the requirement that a compatible reader be able to reopen and interpret it. The owning handle carries the responsibility to release the region. The nodes are ordinary ADTs callable through their initialized receivers. CoD prohibits transitively embedding whole-region owners in user-defined ADT fields. A `Pair` containing an owning handle for each child is therefore unavailable. A factory can construct a private region with a typed entry in its root and hand ownership to its caller. Alternatively, a caller supplies the writable destination `G`, and the constructor returns a borrowed `ref … in G`. The existing return-only contract also describes delivering an owning region and a separate entry reference tied to that actual owner. Retaining only a borrow beyond release is invalid. [Owner-bearing types](RegionalOwnership.md#owner-bearing-types-are-intrinsic) · [Region construction](ConstructionAndAcquisition.md#region-construction-and-named-root-initializers) · [Result-bound owners](ConstructionAndAcquisition.md#result-bound-owners-and-ordinary-liveness)

In the grammar builder, an operator joining two initialized rules in the same `G` can allocate a parent and link its two children. In `choice(p, p)` both edges can designate the same receiver. Each entry still executes the rule under the current cursor and effects. For a chain of `n` leaves, adding one parent per composition builds `n − 1` parents. Giving **each binary operator** a fresh owner and importing its entire left prefix on every step instead gives quadratic cumulative node visits for a left-associated chain. This is an algorithmic comparison under the stated copying policy. The builder can equally fuse a known pair into one typed policy object, as in the invoice example, when its specified observations agree. If independent source graphs really must be imported, specify which bits to transfer, how to map each distinct source node to a destination node, when to establish recursive edges and when the new entry becomes visible. A private failed build can be discarded. A failed append in an existing region may leave unused allocations. Keeping the previous entry usable does not require promising allocator rollback. [Graph transfer, sharing, cycles and failure](RegionalAndLexicalStorageRefactor.md#graph-transfer-with-growing-source-or-destination)

**What still needs type evidence.** In a finite grammar, model different layouts as alternatives of a named rule type, or use concrete typed fields for a particular composition. A recursively typed field supports a grammar with an input-dependent number of nodes. Specializing only the shape of each source expression leaves a question for a loop such as `acc = choice(acc, next)`, which needs one stable type across iterations. For an open library, the hard operation is storing two unrelated third-party receivers as children while preserving the fact that each can produce the promised value under **this invocation’s** output owner `N`. A stored `Map` must also connect its child's intermediate result to its transformation. Owner `G` proves neither relationship. A release can close the set of implementations in its selected module world. A stable open regional reference supporting additional receiver layouts in a later reader would be a separate commitment about type evidence, layout compatibility and method lookup. [Nominal types and heterogeneous fields](DomainLanguageDesign.md#abstract-types-and-data-declarations)

**Experiment that decides the next step.** First build a finite expression grammar in a private `G` with a shared leaf, a consuming recursive parenthesized rule and an explicit `Name → Expr` adapter. Return its owning region, leave the factory, and drive the entry twice with fresh callbacks and distinct output owners. Release the first AST and read the second. Reopen the grammar under a compatible reader at a different mapping address. Check that sharing survives and the reference parser's values, exits and errors agree. Reject an unadapted `Name` on an `Expr` branch. Then ask whether a new module's rule with a different layout can satisfy the same protocol without editing the library's generic choice implementation. Failure at this second step identifies an open-rule representation problem even if independent ownership already works. The repo records bounded same-region cyclic construction in the seed and separate outstanding frontend work for direct call operators and `here` execution. These experiments are proposed, not reported executions. [Receiver evidence](https://github.com/complyue/cod-project/blob/b7fd6327984f537e2256ca14383bbeedd7e833bd/tests/cod/language/README.md#data-call-operator-coverage) · [Recorded cycle and callback coverage](https://github.com/complyue/cod-project/blob/cac10f6204e5d2665a914088e93a533ca43c8cf2/tests/cod/language/README.md#L222-L232)

## Workloads and decisions

Use the reference interpreter and a CoD driver on the same inputs. Capture callbacks entered, semantic value or error, residual offset, diagnostic offset and items, hints, delayed reports and published roots. For owner/cleanup cases, additionally observe validity after unwind, reuse and release. A trace is a proposed differential oracle. This document reports no executable CoD parity results.

| Workload | Required observation |
| --- | --- |
| `char('a') *> char('b')` on `ac`, under plain choice and under `try` with right `char('a')` | Plain choice returns `cerr` at 1 and skips the right. With `try`, the right succeeds consumed at 1. A single `chunk("ab")` mismatch is already empty. |
| `try (char('a') *> char('x')) <\|> char('y')` on `az` | Both branches fail empty. In 9.8.3 report offset 0, expected `y`. The older roadmap pin reports offset 1, expected `x`. Also compare equal-offset expected-set union and a custom error at the same offset. |
| Empty left success followed by downstream failure on `ab` | The `pure('x')` example above must fail. Count zero invocations of the right alternative. |
| `lookAhead (char('a') *> char('b'))` on `ac`, then wrap it in `try` | First returns `cerr` at 1. The wrapper returns `eerr` with state 0 and error offset 1. On successful AST lookahead a caller reads the returned node after input restoration. |
| Recover `char('a') *> char('b')` on `ac` using `pure(fallback)` | Empty success at residual offset 1 with eligible expected-`b` hints. A failing recovery instead returns the original failure at 1. |
| One grammar, two runs, one nested invocation | Use different input and output regions. Release one output, use the other AST and run the grammar again. Reject a grammar/result alias, wrong-grammar child or escaping callback. Inject failure during delivery and verify cleanup with no second arm. |
| Value-dependent production and recursive receiver | Read the left expression and operator, consult the active precedence/fixity environment, then parse the right side at the selected threshold. A weaker operator belongs to the enclosing production. Equal-precedence left/right grouping and a disallowed nonassociative pair expose incorrect state restoration. Parse `((x))` through the same receiver to detect shared invocation state. [Edh production](https://github.com/e-wrks/edh/blob/a2e9b95ef1f84cc5677499512c69d4b03a12cbdc/elr/src/Language/Edh/Parser.hs#L2219-L2278) |
| Two missing initializers and a later valid `return` | Recover through EOF, publish two distinct zero-width error nodes in the expected roles and retain the return. No losing branch publishes an extra node or report. A bounded-resource run instead reports incomplete processing. |

The first experiment uses concrete ADTs, four synchronous callbacks and independently constructed grammar/output owners. It can settle routing, diagnostics and ownership before choosing a new value type. Reopen the bound-procedure-value decision when a program must return a selected receiver through a common lexical interface. Reopen regional protocol references when an application must save and later call unrelated third-party receivers in one grammar. Compare that workload with specialization, including source readability and proof of child/output ownership. Publish any remaining observable differences against the pinned reference before claiming Megaparsec compatibility. The [roadmap](../docs/DesignTopics.md#production-parser-combinators) gives the independent trigger for a later booter backport.
