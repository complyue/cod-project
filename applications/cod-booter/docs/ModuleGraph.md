## Owners across a visit

| Lifetime | Contents and use |
| --- | --- |
| Compilation graph G | Canonical keys, stable invocation-local module IDs, visit states, edges, and published spellings, interfaces, command and literal ranges. A checked entry becomes visible only after its required fields and ranges are initialized and the module succeeds. Retain the graph through final output. |
| Module visit F | A fresh CoD frame and typed workspace for each active visit. CoD computes checked counts and placement for tokens, AST nodes, dependency candidates, bindings, facts and commands. Raw storage gains its element type and readiness through checked construction. |
| Indexed source revision S | One successful owning acquisition per opened revision. Reacquire immutable source bytes and the matching line index from that same S for successive local stages. End each native loan before visiting a child. |
| Diagnostic destination | The launcher supplies separately owned storage. CoD resolves a span against its own revision while live. A dependency failure reported to the parent uses its requesting import span. An open failure without a source position retains its OS error. |

A suspended parent may keep its F and S. Across a child call it retains IDs and spans for graph data and reacquires views before use. An ID requires the graph it belongs to. Publish the required bytes or typed rows in G before their source owner ends. Growth must preserve actual-owner evidence. In particular, [consuming region resize](../../../design/RegionalAndLexicalStorageRefactor.md) requires accounting for the owner and all live dependent uses, including handler and cleanup bindings. A stable module ID alone cannot keep a borrow valid across replacement. The design permits storage strategies that avoid replacing a borrowed region.

Use named sum alternatives for states and syntax nodes with differing payloads. For example, a literal has its value, a call has its callee and argument indices, and a return has its applicable return payload. Keep the common half-open source span, the applicable operator anchor, and the association with the owning syntax revision. A consumer matches the constructor before accessing the variant fields. Child indices retain their meaning when the backing relocates. Use enums for simple closed codes. Project initialized native command rows at the LLVM boundary; the CoD AST layout is private to the compiler.

## First indexed AST path

The first workload parses a module containing a named procedure that returns an integer literal and a call that consumes its result. [ExpressionParser](../src/ExpressionParser.cod) constructs literal, call and return alternatives, together with the module, callable, block and argument structure the input needs. [ParserInput](../src/ParserInput.cod) appends complete nodes. [OperandChecking](../src/OperandChecking.cod) matches the call and resolves its callee; the parser records the callee expression's node ID. [ModuleLowering](../src/ModuleLowering.cod) consumes the checked nodes and emits the corresponding constant, call and return. Node IDs identify entries in one table. That table's frame associates its spans with the particular source revision used to build it, including when a source loan ends between stages.

Use a table-private slot type to keep capacity separate from valid syntax. In this source fragment, `ExprNode` has a half-open span and a typed sum payload. F is the writable workspace owner; `capacity` and `completed` are already established.

```cod
data AstSlot = Vacant {} | Occupied { node:ExprNode; };
array AstSlots[u64]:AstSlot;

ref slots = make AstSlots(capacity, make Vacant {}) in F;
# At the next unpublished index, after checking index == used and index < len(slots):
slots[index] <- make Occupied { node <- completed; };
```

The length and the complete fill argument are each evaluated once in order, including for length zero. Each slot initially holds an independent Vacant value. The parser constructs the complete next row before publishing the new root and used count. Readers check membership of the ID in the published prefix and project fields only for the matched constructor. A physically in-bounds vacant slot cannot be consumed as a syntax node. An ordinary typed reservation can stage a chosen constructor at a known target; it supplies neither the array length nor a completed fill. [Named-array placement](../../../design/ConstructionAndAcquisition.md#source-migration) · [Reservation](../../../design/ConstructionAndAcquisition.md#typed-reservation-and-completed-construction)

This application qualifies the concrete finite layout. All node and slot alternatives contain only direct, recursively bits fields, tags and indices. Transfer preserves the selected constructor and its initialized fields. Inactive fields and padding supply no payload. A native implementation may specialize fill and transfer under the same observable evaluation and failure rules. Adding a stored reference or a resource field requires revisiting this representation. [Bits classification](../../../design/ConstructionAndAcquisition.md#bits-classification-and-representation-obligations)

For growth, create a filled replacement array under the live workspace owner, transfer the occupied prefix at the same indices, and change the table binding only after success. Existing references still refer to their original storage. Consumers carry IDs across the switch and obtain current views through the table. In this path published AST rows are append-only, so no consumer retains a projected field across a change of active alternative. On capacity or construction failure, the preceding published range and root remain usable. Allocation and cleanup keep their ordinary effects. Consuming a region with `resize` has a different ownership and failure contract.

Verify an emitted object returns or reports the expected literal through the named call in both seed modes. Also verify zero and multiple slots, a write leaving its neighbor vacant, independent widths and aligned payloads, rejection of a non-bits element on this transfer path, wrong-table or unpublished IDs, a mismatched arm, stable IDs and spans after growth, and failure before replacement. Keep an isolated implementation until the existing production syntax coverage can switch to the typed table. Delivery uses the actual CoD compiler path and retains its provider and object workloads.

### Frame and node identity

When a visit opens its owning source revision S, the CoD compilation graph G issues a fresh invocation-local revision key. Frame F associates that key with S, one logical AST table and its published count. The stored bits type is `data NodeId { revision:u64; index:u64; }`. A constructor with an optional child represents absence separately, so row zero is usable. Growth preserves this table’s key and indices. Independently rebuilding a table requires a fresh key. A new open gets a fresh key even for the same path, bytes or backing address. Keys issued in G stay spent through failed visits and retries. Check for exhaustion before reuse or wrap and follow the existing failure and cleanup path before publishing a frame.

The parser issues IDs for published rows. Given the originating compilation and a live frame, lookup checks the ID's revision against F, its index against the published count, and the slot's `Occupied` constructor before projecting its node. For a source span the visit borrows bytes and the line index together from F's actual S. Resolve the span within that loan. A parent can reopen a loan on its own S after child reentry.

Two compilations may both issue `(revision = 1, index = 0)`. Their IDs are meaningful only inside their originating G. Keep IDs private to that compilation's parser, checker and lowering data flow. A nested compilation starts with its own inputs and returns its ordinary output or status. Its caller resumes with the original frame. Any interface that could mix IDs from independent invocations must establish their origin separately before lookup. A numeric match supplies neither that evidence nor access to storage. Native interfaces receive their existing source loans or completed outputs. A process-wide key allocator is unnecessary.

Exercise two real frames in one compilation whose occupied rows have the same index, and reject each foreign ID before projection. Reopen the same path and check that the old ID fails. In nested independent compilations, exercise colliding numeric pairs and verify that each call resolves its own source span and restores the outer frame. Keep the valid-ID growth and failed-publication checks in the parser-to-object workload.

### Parsing nominal sum declarations

An ordinary data heading followed by `=` introduces one or more named alternatives separated by `|`. Each alternative has its own braced field list. The parser needs this form to read its own representation of an optional syntax link.

```cod
export data NodeLink = NoLink {} | LinkTo { node:NodeId; };
```

Store a typed sum declaration and an ordered sequence of typed alternatives in the frame’s syntax table. Preserve the heading, including any parsed parent, and the ordinary module-item export marker. Each alternative retains its name, its span through the closing brace and its own fields. Reuse the product-field reader for their shared grammar, preserving order, type, binding mode and target access. Start a fresh field list for each alternative. The reader returns an absent last field for both a valid empty list and a parse failure. Check the diagnostic before accepting a fieldless alternative. Use the frame’s revision-bound links and checked lookup for all children.

In both seed-built modes inspect the actual `NodeLink`, `ExprPayload`, `AstSlot` and `VisitSlot` declarations. The two occurrences of `Vacant` must remain accessible under their own declarations and source revisions. Accept a single alternative. Reject a missing alternative, a trailing separator, `||` between alternatives, a malformed field and a C-layout sum. Preserve the existing product and C-record paths. On the full sources, distinguish passing the original declaration site from checking the whole module. Until a semantic consumer supports the declaration, issue a located rejection before publishing an interface or emitting output. Binding constructor identities, selecting them across modules, checking payload patterns and lowering uses have separate review scopes. | NameResolution, DeclarationTypes, NativeDeclarations, ModuleExports | Match the syntax for names, signatures, selections and native declarations. For example, the parser records a trailing `here` call, the receiver specification and its body. Row zero, an absent optional child, an unpublished or vacant row, and a valid node of another constructor have distinct meanings. A failed lookup cannot supply a default child or a partially published declaration. Constructor-specific forms such as a bare return may represent absence in the constructor itself.

Verify each family on its existing accepted and rejected sources, including ordinary and native `here` calls, owner or receiver mismatches, completion and diagnostic spans. Check the complete isolated CompilerCLI declarations and run the named-call object in both seed modes. ## First dependency edge

**Native path bound to its actual owner.** Use one nominal `PathOwner` for borrowed `Path` values. The launcher lends a ready input path under its live activation. Establish the root's canonical key through its own OS path, preserving source-open diagnostics. The launcher's output-name loan keeps its original owner. CoD can acquire a separate empty owner for a child. An ordinary native operation accepts a writable destination, the selected parent path and a bounded view of the decoded child spelling. CoD handles module selection and escape decoding. Native code resolves a relative spelling against that parent's canonical directory and handles absolute paths according to the host path rules. Reject embedded NUL before calling a NUL-terminated OS interface. Canonical key bytes keep their exact native representation and length. CoD compares and interns them without passing them through `String` or `CString`.

The provider installs the completed path once in the selected destination. Until then it must prevent publication of a `Path` or key loan. On failure it cleans partial native allocations, preserves the failure information and leaves the empty owner safe to release. A later attempt to fill a ready owner must preserve existing loans. The path and its bounded key view then borrow the same actual owner. Intern the key into G while that view is live. `SourceRevision(path)` borrows the path during open and establishes its own independently owned revision. Keep a parent path owner available while child path resolution needs it. Before visiting a child, end the parent source loan, the canonical-key byte loan and any graph-element views that growth can invalidate. Retain the graph IDs, parent import span and independently live resources. Diagnose the failing import against its requesting source.

**Storage for the first edge.** The delivery workload uses a real in-memory region for G. It stores canonical key bytes, visit states and the published ranges needed after F or S ends. Links and ranges in G must survive relocation. Resolve them against the live G and form bounded native views only for the call that uses them. For table growth within available regional storage, construct a replacement, transfer the published prefix and install the new table after success. Growth of a table confers no permission to resize the underlying region in place. Across child reentry retain stable IDs and reacquire views from G afterwards.

An isolated root-to-child probe may use named arrays in the compilation's lexical scope to verify CoD path selection, interning, traversal and handler restoration with real files. Keep the same graph operations and verify regional placement, relocation, actual-owner bounds and release on the delivery path. An absolute element pointer in a lexical array descriptor cannot be stored as a regional link. Bring the intended regional source and the smallest required seed increment into the next review together.

### First-edge implementation

Only canonical backing can lend a key or act as the base for child resolution. Keep the original root input available to `SourceRevision` before canonicalization. The launcher supplies the address of a valid owner record as the same actual A for its input path and output-name loan, and keeps the diagnostic owner separate. The checked constructors for the owning resource and borrowed path report their declared failures; a failed borrow leaves the actual owner live. Expose the canonical-key loan through a CoD procedure. It checks the actual readonly owner with a private ordinary C readiness predicate returning `u8`. **Region and table holders.** The module index uses direct bits roots for the module ID high-water mark, the published key-byte extent and the next fresh source revision, for example `region GraphRoot { used:u64; key_used:u64; next_revision:u64; }`. The regional seed slice covers a lexical owning region holder, acquisition with fully initialized direct bits roots, root access, finite bits named arrays in that actual owner, and cleanup on success and failure. The checker establishes the root schema, write access, actual owner, layout and readiness. LLVM resolves a transient element or bounded native view from that owner and a checked locator. Regional storage contains the count and aligned elements; arithmetic covers header, padding, payload and zero length. The C runtime reuses the existing raw storage open, aligned reservation, address and release operations. Graph types and array-element interpretation stay in the compiler language.

To replace an initialized lexical table binding, a growing helper receives its writable slot explicitly, for example `ref var modules:Visits in G`. The caller passes `modules`. The formal names that same lexical slot through declared place aliasing. The slot's lifetime and writability are independent of the target region G. Ordinary array readers borrow the current target. The helper allocates under G, transfers the published prefix, then installs the finished replacement with `modules = replacement`. Forward this same place through recursive helpers that can grow the table. A parent resuming after the child reads the current holder and resolves its saved ID again. Previously selected references retain their original targets subject to the usual lifetime rules. On failed growth the former holder and published counts remain usable. Staged allocations in live G still belong to G. Expose a completed module and its ranges only after all of its required work succeeds. The bounded seed increment may implement initialized `ref var` named-array parameters, slot forwarding and their negative checks in the parser, checker and emitter. A fixed slot, temporary or incompatible target owner cannot supply that formal.

The growth helper can use the same source with either placement. Its caller has established that more capacity is needed, and the helper checks the published prefix before writing the replacement.

```cod
proc grow_visits(ref var modules:Visits in G, used:u64, capacity:u64) -> void
    where {owner G} {
    assert used <= intrinsic (len)(modules);
    assert used <= capacity;
    ref replacement = make Visits(capacity, make Vacant {}) in G;
    for (i in 0u64 .. used) { replacement[i] <- modules[i]; }
    modules = replacement;
    return;
}
```

### Named-array transport for the first edge

For the finite bits arrays used by `grow_visits` and the typed booter, the seed owns the private array layout. Preserve the existing source bounds-check policy. Construction and native loan validation still require a representable extent.

A retained regional selection identifies the actual G and the table's locator. An element selection also retains its index or equivalent locator. Resolve against that owner at use. Generated code may keep a physical address across operations only with proof that the backing stays stable throughout. This applies to the fill source across allocation, an indexed destination across RHS evaluation and a forwarded lexical holder across reentry. Saving the holder's *place* allows a later read of its current target. Saving the *selected table* keeps the earlier target even after replacement. Storage-form tags and transient header addresses grant neither owner identity nor access.

Preserve the lexical requirement of existing lexical-only operations.

A writable element store reaches the lent bytes. Callback teardown expires the temporary view even if the owner survives. Empty views require no base dereference.

Verify the same growth helper in a lexical owner and an actual region. Forward the same initialized writable caller slot through a child. After replacement, read the old table through a saved borrow and the replacement through the caller’s slot. A caught failure *after* assignment must expose the completed rebind to the caller. A failure *before* assignment preserves the old slot and publication counts. Check same-offset distinct regions, alignment and overflow, plus a legal relocation or address-independent layout probe. ### Module index and visit policy

`ModuleIndex.cod` owns the CoD types and operations for stable module IDs, the graph roots, canonical byte ranges and visit rows. An ID is an index within its originating G. `ModuleKey` contains half-open offsets into G’s published key bytes. An initialized `VisitSlot` is vacant, visiting with a key and source revision, or checked with the completed interface ranges. Bound row access by the ID high-water mark and match the row state. A vacant slot supplies no module. The compilation activation owns G and its lexical table holders. `ModuleGraph.cod` drives source discovery, open, cycle and depth decisions, child visits, diagnostics and the transition to checked after successful compilation.

1. Borrow the canonical key from the prepared path owner. Compare the length and exact host bytes against existing keys and return a typed hit or miss to CoD. End this loan. A checked hit reuses its ID. A visiting hit goes to the cycle policy. Both lookups work with full tables and consume no new graph space, ID or revision.
2. On a miss, retain the key length and the same live, immutable path owner. Check capacity arithmetic for the new row and bytes. Grow the tables under G as needed, preserving their published prefixes. Take a second bounded loan from that owner and transfer the bytes into unpublished space. The size check, growth, second loan and publication run without another insertion or child visit. The loan callback only writes the reserved bytes. If a visit intervened before staging began, repeat lookup and calculate fresh offsets from the current holders before writing.
3. Associate a fresh revision with each successful source open. Publish the complete `Visiting` row and its validated key range before visiting children, with all fallible preparation finished and no intervening callback between the publication writes. Publish `Checked` only when the module succeeds and its interface ranges are complete in G. A failed insertion leaves earlier entries usable. Private allocations may remain in G. Issued IDs and revision keys stay spent. If traversal continues after abandoning a visit, its row must cease to match as active. No retry policy is required for a failed compilation that exits immediately.

In both seed modes, compile and link a root whose result depends on a named definition in a real child. Force table replacement and resolve the parent’s saved IDs through the current holders. Check equal-length keys that differ in their last byte, two spellings of one canonical key, distinct graph instances, a checked hit with exhausted append capacity, and a failed miss that publishes no entry. Preserve the parent import span and the previous output on child failure, and check disposal on both paths. Use the production CoD index and visit code for this proof. The full dependency graph, provider parity and protected-exit workloads retain their separate acceptance.

### Selecting and publishing a completed visit

`ObjectCompiler.compile_object` enters the named root visit with the original input path and diagnostic destination. Parse once under a loan of bytes and lines from the opened S. F outlives that loan and owns the typed AST, its revision key, each requesting path span and the decoded bytes for each outstanding edge. Store decoded ranges separately from original source spans so a later edge cannot overwrite an earlier spelling. End the source loan before invoking the scoped dependency handler. After child work, reacquire the current G tables from their holders and borrow bytes and lines again from the **same** S. On a child rejection use the saved span in the requesting parent revision. Root open failure retains the original OS error.

`ModuleFrontend` passes each selection to `ModuleExports` with its actual table and spelling owner. A builtin path uses the immutable catalog B. A file selection requires the resolved child’s `Checked` row in G and its published export range. Both branches use the existing selection algorithm, including its access, kind and module interpretation checks. Pair each lookup with the spelling bytes from the same store. In the existing selection records zero identifies the builtin namespace and a file module uses its checked graph index plus one, distinct from the absent sentinel. A missing file or export cannot resolve through B. A re-export may change the public spelling and publishing module while preserving the original declaration, checked failure and owner relationships. Interface lookup uses the defining module and declaration.

Use the published extents for exports, spellings and interface rows at every reader, including declaration and operand checking. A bounded view or a checked count suffices. Walk interface headers and their declared entries as units. Prove the header and all its entries lie within the published prefix before indexing any of them. A zero interface kind cannot identify a header, and is valid in a parameter or member row. Reserved or partly staged rows remain invisible even when their contents resemble a valid header.

After all child visits succeed, the parent uses the next artifact function base for its checked lowering plan. Check that the base plus the plan’s full ID extent is representable before forming local IDs. The extent can include gaps for syntax nodes. Published callable interfaces and local definitions use the same base. A call to a published child already has its artifact ID. Reusing a checked child reuses that ID. Only the root supplies the entry. Keep stable module IDs independent of this postorder numbering.

`ModuleGraph` stages and bounds-checks the interfaces, spellings, commands and other unit material before committing. Grow graph tables from their published prefixes and complete all fallible work before exposing the new counts and `Checked` row. Execute the final updates with no intervening callback or fallible step. A failed visit leaves earlier publications intact and the failed module unavailable. G releases any private storage it acquired. On root success the dispatcher reaches the [LLVM construction operation](#constructing-a-linked-object-from-completed-units) after all visit frames and source acquisitions have ended.

Exercise builtin and file imports in the same root, same-spelled functions from distinct files under local names, and two paths to one canonical child. Check a missing or wrong-kind selection, an empty interface prefix, an incomplete header, and a plausible row beyond the published boundary. Fail publication in a second child and verify the first child’s published data, the second import’s span and the previous output. Use the real parser, checker, lowering and dispatcher in both seed modes for the [linked object acceptance](#constructing-a-linked-object-from-completed-units).

## Reentry and completion

The compilation activation owns the graph and enters the named root visit. Each visit installs the scoped dependency procedure for its current frame and invokes it with `behave` for each discovered edge in source order. It reuses checked modules and applies the current compiler profile's cycle and depth checks to active visits. On a new visit it opens the child revision and creates its frame. Once all required children succeed, the parent binds, checks and publishes using their stable IDs.

The first root runs with no preinstalled dependency handler. A lookup while executing `behave` sees the current installation. An actual definition-activation snapshot or `touch` dependency must still be satisfied at activation. Recursive calls can use ordinary named CoD procedures. A nested compilation may execute the same lexical installation site for its own graph and restore its predecessor on exit. The application needs neither a stored handler nor a new rule for recursive capture or method-family composition. [Definition-installed procedures](../../../design/SymbolicDynamicScope.md#definition-installed-effectful-procedures)

Normal return, rejection and exceptional exit preserve the parent binding and frame. Release each successfully acquired resource exactly once in reverse acquisition order within its lifetime. A failed native acquisition cleans its acquired prefix before reporting failure. An abrupt CoD completion crosses a native loan only after its protected cleanup. A failed visit publishes no checked entry for that module. Retain completed graph data needed by LLVM after source mappings close. File output follows the existing publication contract.

### Dependency handler activation

Register the dependency method once in its defining module world. When a visit reaches the definition, prepare a private record in that visit’s live activation. It supplies the checked method and frame interpretation, the lexical places the handler uses and their actual owner evidence. Complete preparation before publishing the record as the symbol’s current binding. The record borrows its inputs. It carries an allocation capability only for a role already proved to require and supply one. A child executing the same site gets a distinct record. The parent record stays live while hidden. An unsuccessful installation leaves the preceding binding in effect.

A symbolic call retains the selected activation through argument preparation and body execution under the existing call order. An ordinary lexical read inside the handler accesses that activation’s slot when the read runs. For example, after a child grows the shared graph table, the parent resolves its saved row ID through the current table holder. `behave` runs with the current dynamic bindings. `perform` replays the selected installation’s required symbolic snapshot. An empty symbolic snapshot can accompany live lexical slots. The checker must establish emptiness from the definition’s dependencies, including `touch` and transitive requirements. A dominating install in the child can satisfy a later behavior demand. It cannot supply a binding needed to activate that installation.

Keep the visit record and all borrowed places valid through every admitted cleanup use. On exit, restore the exact predecessor, including the root’s initially unbound state, before execution resumes outside the visit. Verify parent → child → parent selection on normal return and a caught child failure, identifying each frame through observable data. Include a skipped install, a genuine missing snapshot binding, and an empty-snapshot `perform` that observes the selected visit’s live lexical data. The real dependency-file workload retains the graph, diagnostic and resource checks below.

### Table holder rebinding in a visit

A `behave` call in the defining visit can invoke the installed handler and have it grow `modules` through an ordinary named helper. At call selection the checker must prove which live installation of this visit supplies the writable slot. Reaching the same source definition in the parent and child establishes two installations. If a child can inherit its parent’s installation on a path to the call, the child’s local slot cannot stand in for the parent’s. A local installation must dominate the call and still be the selected binding on every admitted path.

Prepare the written arguments normally. If they complete, the handler sees the then-current contents of the selected installation’s slots. If an argument throws, its completed side effects are observable and the handler has not run. On return or throw from the handler, propagate its completed holder writes to the defining visit. A failed reservation before assignment leaves the entry selection in place. A successful assignment followed by a throw leaves the replacement installed. Restoring a child’s handler binding does not roll back a write to a shared graph table holder. An independently saved reference still selects the old table.

Verify these observations through the real growth helper in both seed modes. Exercise recursive visits with distinct slots, ordinary-argument reentry and an argument failure before entry. Check that a mutating call lacking proof of its selected frame rejects, and that the caller cannot reuse an equality or other refinement established only for the former selection.

## Constructing a linked object from completed units

Before releasing a visit’s indexed source S and workspace F, CoD stages its checked commands, required literal spellings and unit metadata in the compilation graph G. Publish the unit row and its used ranges together after all required transfers succeed. Only units with emitted commands enter the native unit list. CoD selects their deterministic order, assigns artifact-wide function identities and marks the sole entry in its declaration. Labels, slots and literal indices are local to each unit. The builtin catalog keeps its separate owner.

Each unit identifies its original source size and canonical source-name byte range in G. The existing LLVM service requires a nonempty name for every unit of a multi-unit artifact and uses it to report a runtime failure at the originating file and byte offset. CoD can reuse the module’s interned canonical key. Preserve the exact native path bytes. For each text literal, retain the original quoted spelling, preserve its revision-relative span and set the command’s one-based index into **that unit’s** literal list. This permits construction after all source mappings close.

One generated operation takes the live LLVM session and readonly views of published command rows, unit rows, literal ranges and referenced bytes under the same actual G. If keys and literals occupy separate tables, lend both published byte ranges. The C provider checks count conversions, descriptor allocation sizes and half-open ranges against the initialized prefixes before forming pointers. An empty literal list is valid. Empty artifacts and units with empty command ranges reject. Supply each multi-unit source name as a bounded, nonempty, NUL-free spelling with a verified or temporary C terminator. A literal uses its explicit byte length. Preserve the command record’s target layout when passing it to the service. [Private LLVM command interface](../../../cod/lang_llvm_commands_c.h)

The provider builds temporary unit and spelling descriptors and calls `cod_llvm_construct_units` once on a fresh session. Its loans and temporary storage end with that operation. On success the session owns the constructed module through verification and emission. A failed construction may leave partial IR. Release the session through its existing owner and skip verification and emission. Free any temporary descriptors and names on every exit and preserve the existing distinction between a backend status and a boundary failure.

In both seed modes, link a real root and child twice with different child results. Check a child runtime failure against its canonical name and original byte offset, and a rejected import against the requesting parent’s span with the prior output preserved. Exercise retained quoted UTF-8 bytes with a nonzero table offset, an empty literal list, invalid ranges and a wrong graph owner. Verify source and frame release before construction, cleanup after projection or construction failure, and parity of the generated provider interfaces. The full graph workloads below remain separate acceptance.

### Target layout for provider rows

Acquire one owning native layout handle for a provider render that needs row layout. Readonly loans select that handle’s immutable target data. Use the current native target selection and ensure target registration is available on the provider command path. Declaration checking alone needs no layout acquisition. The service can create a target machine to obtain its data layout, then release the machine. Keep the layout and any LLVM context used for queries live until their last use. Dispose of diagnostics and partial acquisitions before reporting a checked acquisition failure. Release a successfully acquired handle once through ordinary CoD cleanup. This operation needs no IR module, builder, assembly printer or output file.

For `i8`, `i32`, `i64`, `f32` and `f64`, return fixed allocation size in bytes and ABI alignment through the generated ordinary `u64` result channel. Also expose the target’s minimum ABI alignment for an unpacked record. LLVM can measure that floor with an empty unpacked struct internal to the query. C receives no CoD record or declaration. CoD maps each checked field to its admitted representation and preserves the nominal identities and restrictions of the C interface. An invalid representation or native handle follows the existing boundary failure path.

For each field in declaration order, round the current offset up to the field’s ABI alignment, record the offset, then add its **allocation size**. A nested record contributes its own ABI alignment and padded allocation size as a field. Validate size conversion, positive power-of-two alignments and arithmetic before accepting a layout.
