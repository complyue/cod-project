## Current implementation boundary

The source compiler implements primitive scalar values, bounded intrinsic-exception values and callable values with complete nested callable capture environments. LLVM-independent checking selects semantic methods and completes demanded value/call obligations before native emission. Proven calls select prepared specializations; general bodies retain independent local operation choices. Concrete methods reuse one native implementation. There is no legacy fallback.

Source discovery loads an acyclic graph of local CoD files and records construction dependencies without choosing executable initialization order. Discovery and initialization planning use explicit continuation frames, so module dependency depth does not consume the host call stack. Active-path cycle detection remains distinct from completed-module reuse. After semantic registration, the checker builds one ordered initialization plan with explicit module origins; checking, native emission and reported execution order consume that plan. File selections currently precede execution expressions in each module; interleaved selections and forward source references require a separate first-reference incorporation proof and receive an unproved diagnostic. Relative paths resolve from the selecting file; repeated resolved paths identify one source module. Ordinary `using`, `using symbol` and `symbol from` select explicitly exported resources, preserve source lookup and do not install a receiver TLS value. Standalone `export` publishes a selected alias explicitly; `export import` publishes the identity selected by that import. Selection alone does not re-export it. Supported resources are ordinary callable families, typed symbols and intrinsic exception types. Selecting a symbol retains its declared type and complete family information. Aliases of one symbol share a TLS slot; identical spellings from different modules remain distinct. Using and identity selection grant no extension permission.

Checked symbol identities, selected family records and source lookup contexts are distinct. A source callable retains its private helper lookup, exception aliases, declaration/result evidence and nested callable context when selected under another alias. Families retain the full admitted-domain proof and captured environment when installed under a different compatible symbol. Source-preserving aliases reuse checked semantic methods and native implementations. Ordinary `import` constructs one receiver family per source identity; repeated aliases share its declarations and extensions. Source families remain unchanged. Both source and imported bodyless contracts can be published without inventing an executable method. Checked signatures retain resolved source exception identities, so receiver aliases cannot erase or retarget checked-throw obligations. Declaration inspection follows the same selected family identity as method lookup. Imported helper queries see receiver contracts; source-preserving selections retain source contracts.

An imported callable retains its source body and lexical/type/symbol context while ordinary callable dependencies use the sequence of explicit receiving interpretations. Private helper calls, recursive/nested callables and retained type contexts follow that sequence. Selection is by source identity, never by matching spellings. Shared inherited definitions contribute once; distinct overloads remain candidates across further imports. A repeated identity or its explicit receiver import can supply its selected interpretation; sibling contexts cannot silently replace one another. Conflicting best candidates reject with both source locations. Unproved equivalence between independently selected interpretations remains an explicit gap. `using` preserves the selected context. The real base/imported-extension/indirect case produces `1,7,1`; a source helper produces `2` through `using` and `14` through `import`. Multi-alias extension warns with `-Wmulti-alias-extension` and supports error escalation.

Native coverage distinguishes source definitions from their selected interpretations. Repeated import aliases share one record; recursion depth creates no methods. Imported methods become executable obligations when demanded, so an unused interpretation hidden by a lexical parameter cannot introduce a false conflict. Complete callable values retain their lexical and dynamic captures; ordinary invocation uses current bindings and `perform` replays the saved bindings. Import changes neither behavior nor cleanup responsibility.

Dependencies contribute initialization expressions once, at the first source-selection encounter. Scan/registration executes none of those expressions. Module lookup does not expose another module’s lexical names. Dependency initialization supports ordinary expressions and resources closed by calls, explicit full scopes or existing iteration effect boundaries; those boundaries restore caller bindings. Retained dependency top-level locals/effects and deferred actions receive an unproved diagnostic. Their process-lifetime contexts and shutdown ordering are not approximated by one shared entry scope. Earlier failure stops later initialization, and a later entry installation cannot supply an earlier dependency read. Module-global access/capture from callable bodies, symbolic import, mixin, same-alias family unions, cyclic construction and symbolic destination-selection forms remain explicit gaps. Entry-extension installation coverage and dependency-write cancellation await the corresponding composition path; this slice establishes neither cancellation nor final-image elimination.

Checked instances record incoming operands' storage roles and passing modes, plus capture storage roles. Callable propagation and native emission consume that same checked frame mapping. Lexical owner-name bindings occupy no payload storage and do not determine operand positions. Native frame normalization preserves the mapping across shared and specialized implementations; incompatible checked input roles cannot reach an emitted call. Read requirements, definite writes, returned targets and nullable-input provenance use incoming operand positions at the call boundary. Those summaries are translated from checked storage through the input map, so captured environment storage cannot shift a caller’s initialization or return-selection obligations. This internal boundary preserves the existing fixed-arity transport and does not define a persistent callable ABI or executable argument-pack representation.

Module symbol declarations require explicit types, including grouped declarations such as `symbol @count:u64,@enabled:bool;` and concrete callable signatures such as `symbol @operation:proc(u64)->const u64;`. The checker records symbol identities and declared types independently of runtime bindings. `typeof(@count)` and `typeof(@operation(1u64))` inspect those contracts without reading TLS, invoking a procedure or requiring an installed value. Selected `std:io` print aliases share one intrinsic identity; its polymorphic type query remains unproved. General runtime symbol-object values, regional runtime bindings and regional symbol-owner contracts remain implementation gaps. Same-scope source symbol collisions with callable, type or value declarations also retain implementation diagnostics rather than selecting a namespace policy.

Symbol access follows the nearest lexical binding, including owner parameters and a named lexical callable’s self binding. A non-symbol local prevents access to an outer symbol. Nested callables preserve their definition-site lookup evidence independently of captured runtime values; caller-local shadows cannot rebind a separately defined callable. Type-only inspection of an explicitly declared callable signature does not inspect its body. Inferred results retain the lookup evidence needed for the expressions actually inspected. These lookup rules apply equally to specialized and general native execution and introduce no runtime symbol objects or default binding.

Supported bits symbols (primitive scalars and intrinsic exceptions) support `effect @x <- value`, runtime `@x` reads and `touch @x` dependencies in module execution and procedures.
