## Current implementation boundary

The source compiler implements primitive scalar values, bounded intrinsic-exception values and callable values with complete nested callable capture environments. LLVM-independent checking selects semantic methods and completes demanded value/call obligations before native emission. Proven calls select prepared specializations; general bodies retain independent local operation choices. Concrete methods reuse one native implementation. There is no legacy fallback.

Supported source includes explicit const scalar results, void callables, unbounded scalar type parameters, exact-argument overload selection with same-T relations, direct/mutual recursion, conditionals, short-circuit booleans, primitive numeric operations and widening, and selected `std:io` printing. Ordinary grouping shares the enclosing cleanup scope; explicit `{{ ... }}` ends its own scope. Plain deferred calls prepare the selected callable and arguments before registration and run in reverse registration order on normal return or failure. Value-callable fallthrough warns and raises unchecked `MissingReturnException`.

An operand that returns or throws has no normal value. Short-circuit boolean operations and `if` conditions preserve that exit; only surviving paths contribute initialization and null-refinement facts. Declared callable-view arguments and named calls with established parameter contracts can exit during preparation, skipping subsequent operand effects and invocation while releasing already prepared values. Named selection may use other operands to establish a concrete parameter type; the exiting operand still produces no payload. Earlier reads, copies and borrows keep their preparation obligations; an invocation that cannot occur contributes no callee effects or checked-exception obligation. A plain deferred call whose preparation exits creates no registration; previously registered actions still run. Print operands, `<-` RHS expressions, null tests, `cause_at` operands, exception operands/causes and intrinsic-exception field operands preserve the same completion boundary. An abandoned assignment establishes no write. In a shared generic body, a context that cannot produce an operand contributes no payload choice; its failure and cleanup paths remain. Static name, arity, known operand-type and conservative skipped-code initialization checks remain; potentially invoked callable paths retain their declared checked-exception obligations. Named/eager calls that cannot establish a signature from abruptly completing operands, and untyped declarations or other unsupported value consumers, retain explicit diagnostics.

Storage operations preserve abrupt completion of their operands. Explicitly typed declarations and `make local T { ... }` initialization can return or throw without publishing an initialized payload or a selected reference target. Declaration groups retain earlier effects and skip later runtime work. An aborted `=` or `<-` writes nothing; an aborted swap neither reads the exchanged payloads nor changes targets. Swap payload reads and null checks occur after both operand expressions finish. Static known-type, callable-kind, destination-access and skipped-code checks still apply; a caught initializer failure does not make its unfinished binding available. Cleanup may preserve or replace the exiting result, including complete callable values.

Eager arithmetic and comparison operators use ordinary method selection and argument preparation. Supported operation names are `+`, `-`, `*`, `/`, `%`, `!`, `==`, `!=`, `<`, `>`, `<=` and `>=`. Unary `-`/`!`, binary forms and parenthesized calls share that path; unary `+` uses `(+)`. The current method subset accepts independently prepared values and explicit external borrowed parameters with established target views and owners. Generic signatures and concrete overloads use the same applicability and specificity rules as named calls. Function and procedure methods may share an operation family when their signatures distinguish them; callable kind is no tie-breaker, and a function cannot invoke a selected procedure.

Target-access qualifiers participate in ordinary method applicability and specificity. A writable target can supply a readonly borrowed input; a readonly target cannot supply a writable borrow. Default value parameters can receive an independent writable copy of readonly input. Among applicable candidates, exact access and narrower type constraints must jointly yield a unique best method: crossed advantages remain ambiguous, with no declaration-order or return-type tie-breaker. Declaration-leading parameter const is callee-local and does not distinguish signatures. Type-leading const does. A concrete expected callable view supplies parameter access when selecting its method; the selected callable still has to satisfy the existing view contract. Shared native bodies retain context-dependent selections even when the underlying scalar argument types are identical.

Operands are evaluated and prepared once, left-to-right, including complete callable snapshots and concrete-to-common exception passage. A missing applicable user method uses the existing checked builtin; ambiguity, an invalid selected body or forbidden selected procedure remains an error. `intrinsic (op)(...)` explicitly bypasses user selection. Generic bodies can contain both user calls and primitive builtin choices while reusing shared native implementations. Deferred calls retain their prepared arguments, and remaining cleanup runs after invocation failure. Constant-bound and null-test proofs depend on checked builtin meaning, not an overloaded token's spelling. Short-circuit `&&`/`||` retain their control flow. Assignment/swap methods and signed-minimum literal syntax with an applicable unary-negation overload remain implementation gaps.

Local scalar `val` declarations provide independent storage. Default and explicit scalar parameters receive callee-local copies; writable parameters and values accept `<-` updates. Declaration-leading const protects val payloads, type-leading const restricts target access, and transfer results are readonly destination views. Grouped declarations preserve source order and initializer-before-binding lookup. Explicit scopes restore outer names; ordinary groups share names and reject duplicates. `-Wshadow` has its own error control.

A `val` may use `make local T` without an initializer and receive a later write. Reads require definite availability and initialization across conservative branch and short-circuit joins. `make local typeof(expression)` obtains a known operand or declared result type without evaluating the query or reading its payload. `=` on existing val storage remains an error because val has no reference binding to replace. Unsupported reference, capture or owner operations do not fall back to bits copying.

Local ref/ptr declarations can refer to checked live scalar or intrinsic-exception targets. Bindings have distinct availability and access permissions; aliases share the target's type, owner and initialization facts. A ref requires initialized storage. A non-null ptr may name an uninitialized destination and initialize it with `<-`. Declaration-leading const forbids rebinding without preventing writes to a writable target. Inferred readonly access stays readonly, and an explicit writable target annotation cannot strengthen a readonly source. Borrowed targets require the exact declared type; independent copies may use ordinary bits widening.

Fresh bits initializers and declaration `<-` create independent lexical storage. Initializing from an existing view retains that storage, including its original owner. Initializer effects execute once even when no payload read or copy is needed. Explicit scopes cannot export an ended target; a local alias does not extend an owner or bypass loop-control capture restrictions. Writes through either name participate in the same branch, loop and cleanup initialization equations. Aliases of caught exception values use the existing immutable capture mechanism. Reference slots carry execution-local addresses without a separate heap allocation.

A generic local ref/ptr declaration can retain an existing borrowed result in one checked context and construct an independent local target from an explicit value result in another. Each initializer executes once under its selected read/view contract. Native frame locations follow lexical declarations, preserving subsequent variables, aliases, loop controls, catch snapshots and nested callable captures when allocation counts or positions differ. The general method selects only the local initialization path; known contexts use direct initialization. Borrowed targets retain their original owners and permissions, while constructed targets end with their lexical scope. Complete callable targets retain independent image ownership and failure-safe replacement. Each context must separately satisfy owner, access, initialization and escape checks; a runtime branch joining a fresh value and an existing target within one checked context remains unsupported. This does not infer a fresh borrowed result or create a runtime owner union.

`[const] [val | ref | ptr] var name [: [const] T] -> lvalue` names an existing lexical slot, including a callable holder. A runtime branch may select among slots of the same storage kind with at most one established target owner. Selection effects run once; no payload copy, independent holder/reference binding or ownership transfer is created. The optional kind must match the selected slot exactly, independently of its current nullness, and type annotations perform no conversion. An alias of a reference slot observes and changes the same binding as the original name. Name availability and access restrictions remain separate; writes, rebinding, null refinement and selected-target initialization use the selected slot's facts. A selected alias observes later mutations through the original name. Overlapping selections conservatively invalidate affected target facts; a write to one selected target does not initialize every candidate.

Leading const restricts writes to the selected slot through that alias; target const restricts derived target access. Independent writable names remain usable. Rebinding through a readonly-target alias still satisfies the underlying slot's declared permissions, owner and initialization constraints. Optional `in O` checks the selected slot's owner, so a lexical reference into O cannot masquerade as storage in O. Ending an alias name's scope leaves the original slot intact; an alias cannot retain an expired slot. A selected alias may outlive an intermediate alias name when all underlying slots remain live. Mixed storage kinds, unproved target-owner alternatives, regional fields and array elements remain implementation gaps. Alias names do not promote ordinary lexical cells into callable captures.

`ptr p:T = null` records a target type without allocating payload storage or inventing an owner. A first non-null target establishes the owner; clearing the pointer retains it. An alias or assignment from an already owned null view also retains that owner. Incompatible owner paths and access after owner expiry are rejected. Repeated iteration scopes represent distinct owners: an outer pointer cannot acquire a fresh iteration owner on each pass. A per-iteration pointer can use its own explicit scope.

Local `ref`/`ptr` declarations may name a current callable owner binding with `in O`. An existing target must belong to O; an absent ptr records O without allocating target storage. Clearing or copying the null view preserves that owner, so a later assignment cannot acquire another one. Owner annotations use nearest-binding lookup before declaring the new name; an ordinary local shadow does not expose the outer owner. Access, initialization, null checks and returned-target lifetime remain independent obligations. Owner names are compiler facts and add no native argument or allocation. Fresh storage requested in an external owner and regional owner declarations remain outside this source slice.

`typeof` supports scalar literals and operations, known bindings, expression groups, same-type conditional branches, intrinsic-exception fields, `isnull`, `cause_at`, and calls with established argument and declared result types. Named calls share semantic overload selection, including access and owner constraints; callable values use their declared signatures. Declared parameter relationships and other operands can establish concrete views for generic or overloaded callable names, including grouped/conditional names, anonymous callable expressions and nested calls. Concrete anonymous signatures also support direct value-call queries. Signature selection checks callable kind, result, owner/access shape and checked exceptions independently of value construction. The same evidence supports contextual arguments in ordinary calls while their actual preparation remains ordered. Queries create no callable-body demand, runtime invocation, payload read, initialization fact, catch snapshot or inferred value capture. Anonymous bodies and their capture lists are not constructed or executed; only their declared callable contracts contribute to the query. Ordinary callable construction still validates its bodies and captures. A separate construction initializer still executes once and retains its ordinary capture and completion rules. Literal validity and operand/signature errors remain checked. Unavailable outer declaration evidence, outer lexical method-family evidence without a value binding, arguments whose callable view cannot be established from declared relationships, arbitrary statement/cleanup queries, indexing and broader construction remain implementation gaps; no omitted-result inference or RTTI is supplied.

Nested callables can query known outer value bindings without capturing their runtime values. Declaration evidence preserves types, access qualifiers and established owner relationships through nested definitions, returned values and recursion. It neither reads uninitialized/null targets nor extends their storage lifetime. Names must be available when the callable is constructed; nearer declarations shadow outer evidence. Explicit capture lists still retain every listed runtime dependency, with ordinary validation and unused warnings. Type-only dependencies require no capture-list entry. Checked contexts distinguish this evidence even when argument and runtime-capture types match. Shared native bodies receive a compiler-selected declaration-context discriminator through the existing private adapters; no outer payload or runtime owner identity is carried. Distinct ancestor owners retain their known relationship, while equality with a new external formal remains unproved without evidence. An ancestor owner differs from fresh storage in the current invocation.

`isnull` evaluates a reference view once without loading its payload. Stable tests refine the corresponding branch, including short-circuit expressions; changing the selection invalidates that proof. A ref requires a proven non-null initialized target. Potentially null reads and writes require a covering catch or the immediate callable's `throws NullPointerException`; module code must catch explicitly. A write checks its selected destination before RHS effects. Discarded rebinding and null tests do not dereference, whereas copying an argument or consuming an assignment result does. Nullness, initialization and valid owner lifetime remain independent. `typeof(isnull(name))` and `typeof(isnull(null))` can supply the bool type to `make local` without runtime evaluation.

Reference `=` selects an existing target of the exact declared type and initializer-fixed owner. It preserves destination access; readonly sources cannot enter writable bindings, and const bindings reject rebinding. A ref requires an initialized new target. A discarded ptr assignment need not read the new payload; using its result as a value does. Conditional, ordinary/explicit scope and guarded expressions can select target views. Scope/finally cleanup preserves the address selected by the expression before cleanup. `<-` likewise captures its destination address before RHS effects, so an RHS rebind cannot redirect that write.

Reference assignment and swap can select existing lexical ref/ptr slots through conditionals, groups and guarded expressions. Slot selection executes once before later operands; cleanup preserves the selected slot address. A reference swap reloads both selected targets after operand effects and cleanup. Chained assignment retains the selected destination slot and its resulting target view. Every possible destination must satisfy availability, type, fixed-owner, access and ref initialization constraints. A mutation of one selected slot conservatively preserves the unchanged alternatives; it cannot establish non-nullness or initialization for every candidate. These selections use execution-local addresses without extra allocation or runtime owner metadata. Borrowed call results expose targets without exposing the callee's reference slots. Runtime-selected ordinary aliases retain their selected slot address.

Builtin `<=>` exchanges the targets of two rebindable reference slots. Both slots are selected once, left-to-right; their current targets are reloaded after operand effects and cleanup. Both directions must satisfy the shared assignment checks before either slot changes: exact type, fixed owner, target access and ref non-null/initialization requirements. Ptr targets can remain null or uninitialized; exchanging addresses does not initialize payloads. Fixed slot aliases participate in the same exchange, and callee-local parameter slots remain independent of caller bindings.

Builtin `<->` exchanges initialized bits at two writable target locations of the exact same type; owners may differ. Operand evaluation retains each selected address, then both values are read before either is written. Operand effects remain visible if a later operand or null check fails; the exchange makes no partial writes. Intrinsic exception payloads retain their category, fields and causes. Both swaps yield void, reject chaining and allow valid self-exchange. Parenthesized calls and explicit `intrinsic (<=>)(...)` / `intrinsic (<->)(...)` use the checked builtins. No conversion or payload allocation is introduced. Callable holder references support `<=>`; complete callable images and regional graphs have no builtin bits swap. User-defined swap methods and plain deferred storage intrinsics remain implementation gaps; defer blocks can execute swaps through their existing late-binding rules.

Finite target discovery precedes initialization checking within each demanded scalar instance. Sequential/branch facts retain reaching targets; repeated loops and cleanup conservatively account for later target changes. Literal zero/single-iteration ranges retain their simpler flow. Reads require initialized possible targets or a valid guarantee for the current selected target. A write through a selected pointer can establish that guarantee without marking all candidate allocations initialized. Rebinding invalidates the guarantee; target versions distinguish a changed selection even when its possible-target set is unchanged. Stable aliases can retain their selected-target guarantee. Native address slots remain separate from source scalar payloads and the private call/exception carrier.

The target catalogue is conservative across mutation boundaries. Future assignments and correlated selections can enlarge its sets; complete alias-history, predicate and queue/category-sensitive mutation proofs remain unavailable. Cleanup equations retain physical-storage guarantees, current-selection initialization and finite target relationships. Facts about targets selected at action entry survive later rebinding, but do not constitute complete alias histories. These are proof limits, not additional source owner or initialization rules.

An explicit `in O` parameter with `where {owner O}` borrows an existing live scalar target. Repeated O occurrences require the same actual owner; distinct owner variables allow equal or different owners. Owner names are implicit const lexical bindings, with no scalar payload or extra region capability. Writable parameters require writable targets. Callee reference rebinding changes its local binding, while payload writes affect the caller's selected storage. Default parameters continue to copy into independent callee-local storage.

Repeated owner roles participate in method matching and specificity. A same-owner constraint can distinguish a method from one accepting independent owners; a candidate must be no worse across type, owner-equality and target-access constraints to dominate. Renaming formal owners does not distinguish signatures. Existing views, aliases and borrowed results carry their established owners into selection. Distinct local scopes, and a callable’s local scope versus an external owner, are known different. Distinct external formal names admit equal actual owners; a selection or selected-callable invocation that requires their equality remains an explicit proof gap when it is unproved. No fallback method or builtin is chosen by assuming those owners differ. Shared native bodies retain checked local selections without adding actual owner identities to runtime values or native-instance keys.

Borrowed arguments prepare their selected addresses once, in source order. An explicit ptr can forward an owned null view without a payload read. Ref requires a proven non-null initialized target; an omitted modifier retains the caller's ordinary read boundary, including checked NPE before later operands. A callee's ptr dereference retains its own checked obligation. Prepared deferred calls save the selected address and observe its payload at invocation; the owner must survive their cleanup scope. Failed preparation or registration does not invoke the callee.

Overloaded calls use checked prefixes and available operand type/access/owner evidence to establish passing modes and contextual callable-view types. A signature query can use current or later operand types, target qualifiers and established owners without executing their source expressions. It shares generic matching, specificity and builtin typing with the ordered checker. Local declarations, aliases, ordinary/full scopes and conditional joins preserve lexical type, target-access and established-owner lookup; unknown binding effects stop subsequent name queries. Declared call results supply type/access/owner evidence without checking or executing callee bodies. The ordinary checker still validates every operand, read, owner and selected body, and verifies that the evidence agrees with the resulting argument types, access and owners. A shared generic body can copy an argument in one checked context and borrow it in another. The selected preparation executes the operand once, preserves value reads before scope cleanup, retains borrowed addresses through that cleanup and finishes any copy before later arguments. Prepared deferred calls use the same choices. Known contexts need no runtime preparation branch; preparation that still needs unavailable evidence remains an explicit implementation gap. Builtin fallback must establish value preparation before later operand effects; it cannot reinterpret an already prepared borrow as an earlier snapshot. Guarded arms with a common normal result type, loop/fold result types and concretely declared callable signatures can supply evidence. Catch parameters and loop controls remain local; branch-only declarations stay conservative. Callable construction is checked and executed at its ordinary source position. Querying an inferred callable signature shares the normal signature constructor, including retained enclosing type parameters. Expected-view-dependent materialization remains contextual, so evidence cannot prevent a permitted throws-view adaptation. These queries establish neither runtime reachability nor binding availability, initialization, capture validity or exception coverage; those remain ordinary checking obligations.

Explicit external-owner results (`-> T in O`, `-> ref T in O`, or `-> ptr T in O`, with target const as applicable) preserve the returned address and access. Ptr results may be null; ref/default borrowed results require non-null initialized targets. Local/default-parameter storage cannot escape as an external result. Return, finally and deferred replacement preserve the selected address through remaining cleanup. An independent const result preserves its evaluated bits; copying a borrowed call result reads the target after callee cleanup. Named and mutual generic recursion reuse native methods without encoding actual owner identities in runtime arguments.

A shared generic body can read a value from methods with different declared result contracts. Local native context selection preserves each method: a borrowed result reads its retained target after callee cleanup, while an independent result carries its evaluated snapshot. These paths join at the consuming value boundary, including val initialization, ordinary value arguments, explicit const returns, operators and callable-result invocation. Complete callable values retain their independent images, and failed copies skip later effects. Discarding a borrowed result performs no payload read; discarding an independent result releases its resources. Prepared deferred invocation likewise preserves the declared result contract. Argument preparation and result consumption share context selection; known contexts need no selection branch. This does not materialize fresh borrowed results, turn an ordinary borrowed result into an independent contract or merge different storage/owner layouts.

Explicit borrowed ptr inputs can refer to uninitialized storage. Callable summaries record the external targets that must be initialized before a read and the writes guaranteed on normal or category-specific failure exits. Substitution uses the actual selected argument targets. Writes preceding a read can satisfy that obligation when two arguments alias; later writes cannot. Recursive and mutually recursive methods share finite summaries. Direct and prepared deferred calls use the same read/write effects. Rebinding during later operand evaluation prevents that guarantee from attaching to a different selection. Failed registration supplies no callee writes. A ptr result can forward uninitialized storage without reading it; consuming its payload still needs initialization and non-null proof.

Returned-target summaries follow actual external targets selected by callable bodies, including finite recursive forwarding. A returned selection can be initialized without every candidate allocation being initialized. The selected address survives later rebinding; explicit returns in finally or deferred actions replace it, while subsequent cleanup can initialize its target. The call proof requires a known actual owner. Null provenance and path correlations remain conservative: forwarding a nullable parameter can retain a possible null result even when a particular actual argument is non-null, and invocation summaries retain possible normal completion even for an always-throwing callee. Null-sensitive cleanup relationships remain incomplete. The private native transport carries an execution-local address and target-type evidence in positions determined by the checked call contract. It introduces no source pointer arithmetic, runtime owner object, public ABI or persisted representation.

Callable values support `func f = ...` and `proc p = ...`, anonymous expressions, named lexical definitions, complete copies, compatible `<-` replacement and nullable ptr holders. Default callable parameters receive independent values prepared before later argument effects. Function/procedure recursion remains native; runtime depth and callable identity do not generate new type instances. Generic parameter, result and local-view contracts can substitute type parameters through nested callable signatures.

Borrowed ptr results distinguish absence forwarded from a formal input from an independently null result. Explicit null returns, clearing a binding, reachable null alternatives and cleanup return replacement remain visible to callers. This evidence follows local aliases, conditional and guarded views, swaps, recursive calls and conservative loop/deferred selections. A saved return keeps its selected address when cleanup only rebinds the source; an explicit cleanup return replaces its target and null provenance. Named, selected and captured invocation use the same summaries. Required-ref checks and uncovered checked-exception diagnostics use the closed checking evidence before native emission. Declared checked throws remain mandatory, and non-nullness proves neither target initialization, access permission nor owner lifetime. General predicate and per-invocation correlations remain incomplete.

An inferred concrete callable view preserves a method's external argument owners, passing modes, target access and declared result owner. Selecting it through a func/proc value uses the same preparation, actual-owner checks, ordered initialization summaries and returned-target proof as a named call. Explicit ref requires a non-null initialized target; explicit ptr can forward an owned absent or uninitialized target, while an ordinary borrowed parameter retains its read boundary. Renaming or reordering formal owner declarations leaves the same argument/result relationship intact. Different owner relationships, value/borrow modes or result ownership remain different callable contracts. The callable holder's null check precedes argument effects and is independent of the returned target's null check.

Selected writers can establish initialization, and selected reference results retain live aliases to existing scalar, exception or callable-holder storage. Deferred calls save the selected callable and borrowed addresses, apply writes only at invocation, and preserve preparation/registration failure cleanup. Generic helpers, recursive forwarding and nested callable captures retain these contracts. Shared native bodies can choose local value/borrow preparation and value/view result paths from the concrete callable contract. Explicit borrowed-holder access needs no image copy; consuming a callable result as an independent value preserves its complete snapshot.

Selected-call proofs follow finite callable values through lexical holders, independent copies, named and selected arguments, explicit results, nested captures, guarded expressions and fold accumulators. Borrowed-holder writes flow back to their possible targets. An unrelated materialized implementation with the same view contract does not affect a call unless its value can reach that call. Reads must be safe for every admitted implementation, writes must be guaranteed by every relevant exit, and returned selections include their alternatives. Recursive writer guarantees and read requirements close with the value-flow evidence before validation. Native local selection consumes the same evidence, joining compatible contexts within each shared method; callable identities do not create new native methods. Declared checked exceptions remain obligations even when admitted implementations do not throw them.

The analysis conservatively joins storage histories and inputs to shared checking instances. It does not distinguish every prepared snapshot, branch correlation or per-invocation argument relationship. Uncovered value sources retain all compatible implementations; absent target evidence does not establish a narrower set. Explicit source annotations for owner-bearing callable views, open generic views and fresh borrowed-result storage remain outside this slice; an already inferred view can pass through an ordinary type parameter.

Generic signatures such as `func apply(f:func(T)->const T,x:T)->const T where T` infer T from the concrete callable view and require the same type at every repeated occurrence. Applicability, most-specific selection and duplicate-signature detection share this structural relation. Callable category, argument/result access and declared throws remain part of the view contract; matching does not introduce variance or adapters. Checked prefixes and available later operand types can establish a concrete view for an overloaded/generic family argument. For example, `apply(identity, 1)` can select an `i64` identity view when apply declares `func(T)->const T` and a later T parameter. Missing or inconsistent evidence remains diagnosed; no new generic inference or callable variance rule is introduced. Runtime evaluation stays in source order. A determined `void` result permits normal completion, while non-void contexts require explicit return after cleanup; both can share one general method. Undetermined result binders remain diagnosed.

Named lexical recursion and module calls use the same signature lookup for operand evidence, ordered preparation and final selection. A recursive call retains its lexical type context and captured environment, prepares ref/ptr/read borrows according to the declared modes, and preserves owner, access, null and initialization obligations. Deferred recursive calls retain the same prepared targets and cleanup ordering. Reading type evidence does not read payloads or execute later operands; contextual callable materialization still checks kind, qualifiers, captures and throws at its source position. Known abrupt completion propagates through strict consumers, conditions, loop setup and plain deferred preparation. A non-producing operand contributes no payload type, access or owner evidence to candidate filtering; the ordered checker still validates operands and selected bodies. Short-circuit right operands and delayed defer bodies do not imply unconditional completion at their source position.

Nested callable definitions retain required enclosing compile-time type bindings in their signatures and local annotations. Their own type parameters remain distinct and can shadow enclosing names. Required bindings propagate through intermediate nested definitions, survive complete copies and returns, and constrain later calls without being inferred again from unrelated arguments. Unused enclosing binders add no context requirement. These type bindings are separate from value capture lists and do not retain ordinary lexical cells. General native bodies preserve the retained type evidence; local conversions use the checked context when operand types alone cannot distinguish the required result. No source runtime type-object API or persistent type encoding is implied.

Callable invocation selects and reads the target before arguments. Plain deferred calls retain that complete selected value before registration, while delayed blocks read the current holder when invoked. A null target fails before argument effects; failed preparation or registration never invokes it. Declared checked throws remain caller obligations, and a function cannot invoke a procedure value. Empty environments need no image allocation. Nonempty environments retain complete nested callable snapshots, including in deferred records.
