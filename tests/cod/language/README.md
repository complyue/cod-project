## Intrinsic exception control

[ExceptionControl.md](../../../design/ExceptionControl.md) (D-17) is the bounded H-267 contract; [K-410](../../../design/DesignAuthorityRegistry.md#k-410) records this implementation increment. `using "std:exceptions" InvalidCapacity;` selects an exact catch identity, with normal local alias support. `try { ... } catch (e : const InvalidCapacity) { ... } finally { ... }` produces the normal or handled value; finally normally yields void, or uses explicit `return` to complete its enclosing callable. A final `catch (e)` accepts remaining intrinsic categories. `throw e` propagates a caught value and `throw;` rethrows the active catch. Finally failure replaces pending completion without adding an automatic cause.

[The focused evidence](exception-validation.json) covers the three intrinsic allocation failures, nested control and cleanup, original failure sites through rethrow, captured/hidden binding restoration, and category preservation through loops. The runtime fault test injects a provider `std::bad_alloc` without exhausting host memory. `python3 tests/cod/language/exception_runtime_tests.py` runs that check plus the key invalid-catch/finally/effect-context cases.

[Typed ownership evidence](ownership-lifecycle-validation.json), recorded by [K-411](../../../design/DesignAuthorityRegistry.md#k-411), covers `owned region packet:Packet <- make Packet(capacity = bytes) { ... }`, `root(packet)`, borrowed versus owned parameters/results, local moves/effect installation, branches and exceptional cleanup. `owned_region_tests.py` checks initialized-root relocation, 19 exact acquisitions/releases, pre-entry conversion failure, abandoned results and invalid owner/view uses. The library fixture exercises exported typed factories and generic forwarding. [K-412](../../../design/DesignAuthorityRegistry.md#k-412) and [the control audit](ownership-control-audit.json) add15 invalid-source checks, selected-owner cleanup, captured/current symbolic owning results and borrowed edits surviving failure.

`throw primary from cause` creates an immutable explicit relationship. Returned/stored errors retain their causes beyond catch exit; `.cause_count` and `cause_at(error, index)` inspect them. Common `SystemException` fields preserve the category on reload. Cause records use execution-local numeric handles, and their backing storage remains until execution exit. Creating a chain can raise a fresh unchained OOM; ordinary propagation allocates no cause storage. This is not a persistence or cross-process format.

## Architecture boundary

[Module worlds](../../../design/ModuleWorlds.md) records independent module worlds, explicit publication, receiver-local same-identity merging, shared vocabulary identities and a separate flat TLS collection of typed symbolic pointers. H-245 forbids editing another module world at compile time and runtime: each module constructs its own world. ## Module publication and implementation contexts

## Supported source forms

```text
symbol x : i64, p : proc() -> i64;
using symbol "std:io" @print;
function twice(value: i64) -> i64 { return value * 2 }
global seed: i64 = twice(3);
effect @x <- seed;
proc @p() -> i64 { return @x }
effect @x <- 9;
behave @print(perform @p);  # 6: definition-time value
behave @print(behave @p);   # 9: current dynamic binding
```

- Scalars `i64`, `u8`, `u32`, `u64`, `f32`, `f64`, `bool` and `void`; decimal integers with optional leading zeroes, floating literals with optional `f32`/`f64` suffix, `true`/`false`, arithmetic, comparisons, `!`, `&&` and `||`. Unsuffixed floating literals use `f64`; mixed numeric arithmetic uses a unique least lossless common representation. Floating operators use native IEEE arithmetic; signed integer arithmetic checks overflow.
- Lexical functions and procedures have typed parameters. Procedures use `proc` or `procedure` and require an explicit result type. `proc p(x:i64) -> i64 { ... }` defines a lexical procedure; `proc @p(x:i64) -> i64 { ... }` defines a symbolic procedure, declaring its typed identity if absent. A no-argument procedure may omit its parameter list. `p(...)` uses lexical lookup and current dynamic bindings; `perform @p(...)` restores captures and `behave @p(...)` uses current bindings. Functions cannot call procedures. Operation overloads also use current bindings.
- `effect @name <- value` transfers bits or acquires a whole-region resource for the enclosing scope; `effect @name = value` rebinds an object or procedure. All effects yield void. `@name` reads. Nested braces restore bindings on exit. Ordinary `@name = value` rebinding is rejected. Each symbol declares one value type, checked before binding; procedure types include parameter and result types. A conflicting binding reports the symbol and both types, including nominal module origins even when local aliases have the same spelling.
- `if (condition) { ... } else { ... }`, with matching branch result types. Blocks yield their last expression; an empty block yields `void`. Semicolons separate expressions and a trailing semicolon does not discard the last value.
- `const ptr a = value, b = value, { ... };` fixes the declaration-group bindings. It does not make writable target memory readonly; `<-` and `<->` may still edit that memory. Rebinding through `=` or `<=>` rejects, including overload/intrinsic calls.
- `<=>` exchanges same-owner pointer targets, and `<->` exchanges same-type writable bits across either the same or different owners. Both evaluate two destinations once, left-to-right, yield void and cannot chain. Parenthesized overloads can be functions/procedures with two explicit external-owner parameters; reference-swap formals denote both actual caller bindings. Explicit `intrinsic` calls retain all builtin checks.
- `for (i in first .. last) { ... } else { ... }` optionally handles **zero body executions only**. Bounds evaluate once. Exceptions do not trigger else, the index is body-local, and both blocks restore their own dynamic bindings. The loop yields void. Initialization after the loop must hold on every normally completing path; a body read before its first write still rejects. `fold ... else` is not supported.
- Module-level `symbol`, `function`, `procedure`, immutable bits `global`, resource declarations and expressions. Global initializers must be bits literals or function calls. Their selected outer user callable must be a function, including for overloaded operation spellings; native explicit-memory operations are also allowed. A procedure overload remains invalid in that position. Local immutable `let` bindings, bounded loops and declared regional arrays support numerical kernels.
- `symbol local : T;` (also `symbol @local : T;`) declares a fresh typed identity; grouped declarations require a type on each name. `proc(T1, T2) -> RT` denotes a procedure signature. `symbol from "vocabulary.cod" @source as @local;` preserves the source identity and type. A standalone symbol declaration/selection supplies no runtime value.
- `using "module.cod" @resource as @local;` and `import "module.cod" @resource as @local;` install the source procedure with its definition/captures under an existing destination symbol. `mixin "module.cod" @resource as @local;` redefines the body in the receiving lexical/dynamic context and installs that result. The destination must be declared or selected before the encounter, even when `as` is omitted. For source-preserving using/import, omitting `as` requires the destination to share the source identity; a different identity requires explicit `as`, even `using "module.cod" @resource as @resource;`. Mixin retains its receiving-context mapping rule.
- `using symbol "module.cod" @resource as @local;` selects both the source identity and its procedure in one encounter; `as` is optional. An absent local name becomes an alias of the source identity. An existing name must resolve to that same identity; otherwise use ordinary `using` with an explicit destination. Equal procedure values or spellings do not establish identity equality.
- `mixin "module.cod" @resource as @local with { @target as @tgt_neuron; };` supplies the receiving module’s `@target` identity for the source-body role `@tgt_neuron`. Unlisted body aliases use the same name in the receiving module. Translation precedes capture/checking, covers reads, writes and procedure calls, and creates no runtime alias map or extra local alias. Using/import do not accept a body map.
- Lexical functions, lexical procedures, types and immutable globals can be selected with using/import. Lexical and symbolic procedure mixin supplies receiver-context redefinition; either may provide a symbol-role map. A local overload of a selected ordinary callable requires import under that alias; using alone grants no extension permission.
- Synthetic system module `std:io` provides `@print` for one scalar and `@assert` for one boolean. These are procedures; functions cannot invoke them or other effects. Use `using symbol "std:io" @print;`, or explicitly select an existing destination. Built-ins have no source body to mixin; source-preserving import can select them.

Prototype expression evaluation is left-to-right; boolean operators short-circuit. Both conditional branches are checked. A symbolic write in a conditional logical operand requires an explicit nested scope, including assignment of the same scalar or region resource again. Integer arithmetic overflow and integer division by zero fail the native program with exit 70 before LLVM can evaluate an invalid operation. LLVM-emitted checks include the offending CoD expression’s file, line and column; nested calls restore the enclosing expression’s location. Native allocation-service errors include the allocating expression’s location before the allocator message. This embeds diagnostic text without requiring source files at runtime or providing source-level debugging. These sequencing, block-result and numerical choices remain reviewable prototype conventions.

## Abstract types and adapter conformance

```text
type Entity;
type Weighted <: Entity;
data Sample { value:i64; }
```

Abstract types have nominal identity and one optional abstract parent; they have no constructor or native object layout. Data products use the existing region allocation/reference path. A separate adapter may `import "data.cod" Sample;`, select the abstract type, then declare `data Sample <: Weighted;`. A consumer may `using "adapter.cod" Sample;` to obtain that identity and the adapter's visible conformance. Using alone does not allow an adapter to add external data conformance. Source module inclusion or selecting only a method does not globally publish its relations.

Methods accept declared abstract constraints and select a unique most-specific parameter tuple without declaration-order tie-breaking. Incomparable specializations are errors. A checked abstract argument can be forwarded through source modules without making the caller's adapter globally visible; returned views retain regional lifetime provenance. Conditional branches with the same concrete data type and owner retain the most specific nominal ancestor guaranteed by both admitted interfaces. This alone does not establish a sibling or child-interface claim. Missing bodies in unused call paths remain harmless; a demanded missing implementation is a compile error. Type selection supplies source-visible associated signatures, including factories whose result alone mentions the type. Bodies are not scanned to discover association; body-inferred result types are not used for method discovery in this subset. Exact occurrences inside supported wrappers count; inherited applicability does not imply mutable wrapper covariance. Bodyless declarations, abstract stored-reference layouts, repeated identical conformance declarations and sum/generic construction remain unfinished. Concrete user data is regional; scalar UoMs remain bits-backed numeric types.

## Intrinsic and procedural operation overloads

`function (len)(value:Box) -> u64 { ... }` explicitly declares an intrinsic overload. `procedure (store)(cell:Cell, amount:i64) -> i64 { ... }` declares a procedural overload; its body can access dynamic resources and mutate regional storage. Parenthesized eager operator names such as `(+)` support both kinds too. These are compiler operation names, independent of any `@len` or `@store` symbol. `(@len)` is a grouped symbolic read; neither `(@len)` nor `("len")` is an intrinsic declaration name.

Calls dispatch on argument types across both kinds. A function cannot call a selected procedure overload; the checker does not substitute a different pure method. Exact matches precede conversion-enabled alternatives, and equal matches remain ambiguous. Arguments execute once with each selected conversion before the next argument. A procedural operation uses current dynamic bindings, including the captured context of an enclosing ordinary `perform`. Pure UoM conversions retain their function-only rule.

`using "intrinsic-library.cod" (len);` selects the source method set with its lexical definitions. Operation overloads require an operator/intrinsic destination; ordinary lexical procedures retain ordinary-name selection and symbolic procedures retain symbol selection. Applicable user methods precede the native primitive fallback. `len(array)` therefore retains native array behavior when the selected methods apply to other types. `(len)(value)` is the explicit-call spelling.

`intrinsic (operation)(arguments...)` selects the checked builtin directly. For example, an `(=)` method can use `intrinsic (=)(lhs, target); lhs` without recursive lookup. Eager arithmetic and existing named intrinsics use the same form. Arguments retain their evaluation order, types, owners, access and lifetime checks; there is no fallback to a user method if the builtin is absent or invalid. `intrinsic ([]=)` therefore rejects. Mixin preserves the explicit selection. Source helpers with independent lexical method tables also retain their ordinary semantics; no user symbol or runtime intrinsic identity is introduced.

Ordinary declarations cannot use literal/control keywords (including `intrinsic`), intrinsic call names or built-in type names. The intrinsic group is `region`, `used_bytes`, `capacity_bytes`, `deref`, `len`, `ref_at`, `store`, `setfield`, `scalar`, `i64`, `u8`, `u32`, `u64`, `f32` and `f64`; `bool`, `void` and `ref` are also reserved ordinary names. Contextual names such as `in` and `else`, record field selectors and `@symbol` tokens retain their distinct grammar. For example, bare `function len(...)` is rejected, while a record field named `len` is valid.

The primary module-form words `type`, `data`, `regional`, `unit`, `array`, `using`, `import`, `mixin` and `conversion` are reserved against ordinary declarations and aliases under H-161. Field names such as `record.type` and symbol names such as `@using` retain their grammar.

`setfield` remains a native primitive with a compile-time field selector. Its overload declarations/aliases are rejected until that selector contract is designed. H-162 selects a distinct `(=)` family: explicit definitions, source selection and calls use the existing typed dispatcher. Its methods need not match `(store)` behavior. Indexed assignment `a[i] = value` calls the separate `([]=)(a, i, value)` family under H-163/H-164. It preserves both container and index types, evaluates each argument once, completes each selected conversion before the next argument, and yields the selected method result. Explicit calls and `using "module" ([]=);` use the same methods. A matching visible method is required; there is no implicit forwarding to `store` or `(=)`. Record-field assignment, intrinsic procedure-body mixin and explicit intrinsic `perform` syntax remain deferred. Existing `store`/`setfield` primitives implement writes within procedural overloads; no runtime method registry, user heap or new regional pointer representation is introduced.

H-270/H-302 requires ordinary `=` to rebind references within one owner and retain destination-view results. Builtin `=` preserves access; selected methods declare and prove their result access. A nonvoid `<-` result remains readonly; a user method may instead declare void. Owner-mismatch diagnostics suggest `<-` for bits transfer. [ptr-assignment.cod](ptr-assignment.cod) checks qualifier selection, chains and caller-visible rebind; indexed payload-writing fixtures remain compatibility evidence outside the complete indexed-reference contract. [RegionalOwnership.md](../../../design/RegionalOwnership.md#const-qualified-reference-assignment-methods) specifies the confirmed matching/body/result rules and the destination-return safeguard.

The lean regression cases in `intrinsic-overloads.cod`, `intrinsic-pure-error.cod`, `intrinsic-reserved-name.cod` and `intrinsic-symbol-name.cod` cover cross-module mixed methods, lexical helper reuse, regional writes, native fallback, pure global initialization, capture/current context, an unused overload's missing binding, native-signature delegation, token-category separation, keyword rejection and purity failure. ## Units and conversion selection

```text
conversion function cm_to_metres(x:f64(cm)) -> f64(metres) {

}
function distance(x:f64(metres*)) -> f64 { return scalar(x) }
```

A unit definition creates a distinct compile-time identity independent of numerical storage. `metres(2.0)` has type `f64(metres)` and `metres(2u32)` has type `u32(metres)`; `scalar(x)` extracts the representation explicitly. Aliases preserve identity and do not add a runtime tag. Methods can define meaningful arithmetic on unit values.

Repeated selections from the same source, duplicate identities through re-exports, and UoM import are rejected. Automatically selected conversion names occupy the lower-priority implicit-method namespace. A local function, global or explicit type alias can shadow them without removing their automatic conversion edges. A shadowing callable does not fall back to a hidden converter when its parameter types do not match. Explicit callable using/import still determines extension permission. Distinct implicit converter families with one spelling require explicit name selection for direct calls; their typed automatic routes remain separate.

`x:f64(metres)` requires that identity and permits lossless representation widening; `x:f64(metres*)` also permits unit conversion. `x:f64(metres*<-cm<-mm)` uses a direct conversion when available, otherwise the declared indirect route. Automatic graph search chooses a unique path. Multiple unresolved paths warn and continue using the shortest route with declaration-order tie breaking, reporting an alternative witness. `--warnings-as-errors` and `-Werror=unit-conversion` turn those warnings into errors. Paths use the call site's selected bundle; route names resolve where the parameter is defined. Exact applicable methods are selected first; otherwise require one most-specific widening/conversion-compatible signature. Numeric widening preserves the unit identity and never supplies implicit narrowing.

The fixture checks all three definitions under captured `perform` and current-binding `behave`. It mixes procedure bodies, not UoM definitions.

A `conversion function` requires one exact UoM parameter and an explicit UoM result; both automatic routing and direct calls enforce that signature. Conversions are functions; they cannot read/write dynamic effects or invoke procedures. The original argument is evaluated once. Calls evaluate each argument and complete its selected conversion before evaluating the next argument, under [H-148](../../../design/DesignAuthorityRegistry.md#h-148). A failing conversion prevents later argument effects. Functions, procedures and overloaded operator spellings share this order. Identity/route checks happen before native compilation, including when a preceding module initializer would print at runtime. The compiler does not enumerate cyclic walks or claim that distinct numeric formulas are equivalent.

## Bounded iteration and numeric representations

```text
function sum(n:u32) -> u64 {
    return fold (i in 0u32 .. n, total = 0u64) { total + u64(i) }
}
for (i in 0 .. 10) { behave @print(i); };
```

`for` is a void expression: its body is evaluated for effects, and its final value is discarded before the iteration scope closes. A reference to iteration-local storage may therefore be the final body expression without escaping that scope. `fold` returns its accumulator, initialized once and replaced by the body's value after each iteration. Ranges include the first endpoint and exclude the last; reversed/empty ranges execute zero times. Endpoints must share an integer type or one integer-backed UoM identity. Each iteration has its own dynamic scope, while procedure writes to regional storage persist until the owning region ends. These are native runtime loops, not compile-time iteration expansion. Scalar/UoM, regional-reference, whole-region-borrow and borrowed record/array accumulators retain their concrete types. A borrowed accumulator also retains one owning region and any admitted abstract interface, which the body result must still satisfy. The loop carries access to existing storage, not a copy of the object. [fold-products.cod](fold-products.cod) updates a structured accumulator and alternates two arrays in one region; [view-fold-validation.json](view-fold-validation.json) records normal/empty loops and rejected owner or interface changes.

A nested lexical scope may shadow an outer local; the initializer sees the outer binding, and leaving the scope restores its visibility. Declarations within one scope must be unique. Function parameters and loop index/accumulator bindings share their body’s declaration scope. Conditional branches and the conditional right operand of `&&`/`||` keep their local declarations inside that scope. [H-149’s naming rule](../../../design/SymbolicDynamicScope.md#local-value-shadowing) concerns lexical values; symbolic writes still require `effect`.

Parameters, ref/ptr/val declarations, loop indices and fold accumulators reject [reserved expression names](../../../design/SymbolicDynamicScope.md#lexical-declaration-keywords), such as `true`, `null` or `if`, before execution. Contextual names such as `in` remain usable. Field selectors such as `.true` and symbolic names such as `@true` keep their identifier meaning.

Unsigned literals use `u8`, `u32` or `u64` suffixes. Integer arithmetic checks overflow, including unsigned underflow; it does not silently wrap. Explicit `i64`, `u8`, `u32`, `u64`, `f32` and `f64` calls convert raw numeric values. Integer narrowing checks range. Float-to-integer conversion truncates toward zero, then checks the mathematical integer range before the native cast; NaN/infinity fail. Integer-to-float and float narrowing may round; finite floating overflow fails. Explicit floating casts may underflow to zero, while an out-of-range source literal is diagnosed. Floating literal validation uses its declared precision, including representable subnormals and values near rounding boundaries. Bare scalar type names are reserved ordinary identifiers. Parenthesized numeric operations can have explicit methods for nominal inputs: the pool-index fixture defines `(u64)` for `SlotsPerSet` and `LocalSlot`, then uses `u64(capacity(j))` and `u64(slot)` at its raw arithmetic boundary. This neither enables implicit brand erasure nor adds an automatic UoM conversion route.

It reproduces the documented `J=16, q=10` arithmetic candidate: 655,350 sets, 112,281,600 slots and final slot index 112,281,599. Boundary/median round-trips cover every class. Distinct class-local/global-set and local/global-slot types prevent accidental interchange; conversions requiring layout remain explicit pure functions. This fixture selects no neural law, final pool geometry, allocation policy or bounds proof for arbitrary caller values.

## Regional storage and function access

```text
unit Neuron;
array Rates[u32(Neuron)]:f32;
data Node { value:f32; ptr next:Node; ptr rates:Rates; }
region symbol @arena;
symbol @rates : Rates;
effect @arena <- region(4096u64);
effect @rates = alloc @arena Rates(4u64, 0.5f32);
store(@rates, Neuron(1u32), 2.0f32);
function total(a:Rates) -> f32 {
  return fold (i in Neuron(0u32) .. Neuron(u32(len(a))), sum = 0.0f32) { sum + a[i] }
}
```

Regions use the existing shilos region allocation/release operations with a fixed payload capacity. `alloc @arena` or `alloc arena` through a lexical region borrow creates an array or regional record; allocated storage remains part of the region until teardown. User code can reuse stable typed slots or array entries through a library free list/pool; this does not release their storage to the system or automatically validate a library item identity. Regional records cannot be stack-constructed or copied/moved. Arrays store contiguous scalar elements with a declared index type; related arrays may share that type. Separate source-ID and weight arrays occupy four and one bytes per element respectively. Product fields use parallel arrays, rather than a hidden array-of-records representation.

Record fields use .field, arrays use [index], and len returns u64. Ref/ptr-marked fields store relative references; their expressions expose the target type directly. Alloc and ref_at return noncopying views. Deref explicitly validates/accesses an existing view; ordinary value positions already dereference it. Nullable pointer access raises checked NPE, while isnull inspects the reference. Same-owner storage and the declared array index identity are checked independently.

Accepted known issue ([H-146](../../../design/DesignAuthorityRegistry.md#h-146)): assigning a record to its first pointer field produces field-relative displacement zero, so the field reads back as null. Ptr fields retain this encoding and behavior. Non-null ref fields reject that unrepresentable edge with a runtime representation guard. Future intrinsic object fields are expected to resolve this limitation; their definition, layout and compatibility rules remain open. Other nonzero-distance cycles are covered by relocation evidence.

Procedures may use `store(array, index, value)`, `store(scalar_ref, value)` and `setfield(record_view_or_ref, field, value)`. The `field` selector names a declared field, as `.field` does; it is not evaluated as an expression. Field names such as `effect` or `true` retain their identifier meaning in this position, including inside parentheses. Stored results survive dynamic-scope restoration. An ordinary value `effect` restores its previous binding on scope exit; whole-region effects admit fresh acquisition and owner-preserving shadowing, with extraction from an existing dynamic owner rejected as described below. `used_bytes` and `capacity_bytes` inspect an explicitly supplied region borrow from a function or procedure. Capacity includes the native region header; allocation requests specify payload bytes.

Functions and their nested function calls may read and modify memory reachable through explicit inputs, including reference fields. Native store/setfield and mutating function overloads are permitted; dynamic binding reads/writes and procedure calls remain rejected. There is no automatic read-only snapshot interval. A copied scalar argument retains its evaluated bits, while a regional view observes actual storage and intervening writes in source order. Multiple parameters can alias the same region. Returned references retain their actual input-region association; this does not permit stored cross-region references or escaping a destroyed region.

```cod
effect proc @read() -> i64 { touch @right; return @left.value };
```

The group evaluates every RHS against the preceding bindings, then installs the new references together. An RHS exception leaves all group bindings unchanged; its own regional edits are not rolled back. Shared owner means one actual region, with the declared root constraint. Object references require a region-symbol-backed live resource. Bits use direct typed TLS storage; neither object nor procedure rebinding accepts effect-arrow.

`touch` adds an explicit procedure capture dependency without reading object fields. A partial `perform` replay that mixes incompatible group owners rejects; adding the companion touch captures it deliberately. `behave` uses current bindings. Every effect returns void. `effect @selected = existing_proc` preserves that procedure's captures; `effect proc @selected(...) -> T { ... }` captures at definition, declares a new typed symbol or validates the existing/imported signature, and restores the previous binding at scope exit. `effect proc @empty() {}` has a void result signature.

A bare object transfer `@object <- rhs`, or `(<-)(@object, rhs)`, uses a user-defined overload and returns void or a read-only view of the original destination. Owner formals such as `dst:Node in d` with `where {region d:Pool}` provide the actual region as d. The overload can call root-policy operations without consulting an unrelated ambient symbol. No transfer fallback copies a graph. Regional read-only views propagate through reads/branches, cannot enter writable parameters/fields, and cannot become writable fold accumulators.

[symbolic-context.cod](symbolic-context.cod) and its vocabulary exercise imported identities, hidden owners, staged failures, touch, existing/inline captures and restoration. [symbolic-transfer.cod](symbolic-transfer.cod) exercises actual source/destination regions, persistent edits and live destination views. The [evidence record](symbolic-context-validation.json) includes focused invalid-source checks and migrated-context regression traces. Complete ordinary ptr/lexical-owner semantics, general scalar assignment places and runtime closures remain outside this native subset.

## Whole-region ownership

Fresh raw resources are acquired with `effect @arena <- region(bytes)` or `owned region arena <- region(bytes)`; typed roots use make. The owning scope releases them; module-owned regions remain live until process exit. A whole-region value cannot be extracted from a dynamic binding: `effect @other <- @arena` and self-transfer are compile errors. A fresh binding may shadow an existing resource while preserving the hidden owner's lifetime.

`perform` can temporarily expose a captured region while another region is bound to the same identity. Both owners survive replay, and the caller's binding is restored. The `region-owner-capture` fixture checks this; `region-owner-move` checks extraction rejection. The native relocation/release harness verifies layout and allocator symmetry independently.

A bare region is borrowed access outside its acquiring effect. `region view = @arena`, `function forward(region arena) -> region { arena }` and corresponding procedure parameters preserve the original holder. `alloc view T(...)` places an object into that supplied region; it neither creates another region nor consumes the borrow. [region-owner-lexical.cod](region-owner-lexical.cod) checks forwarding, zero/repeated folds, payload allocation and access while the dynamic name is shadowed. [region-borrow-validation.json](region-borrow-validation.json) also covers extraction rejection after forwarding, whole-region and interior-view escape rejection, pool relocation and a 96-module borrow chain. Returning the borrow does not extend its lifetime.

D-17 distinguishes owning-holder availability from the actual region lifetime. Fresh `make` results, owning locals/calls/results, effect installation and normal/exceptional joins are implemented and covered by [the lifecycle audit](exception-ownership-validation.json). [Earlier lifetime evidence](owner-liveness-validation.json) retains its effect-owned scope. General qualifier/assignment, owner reinitialization, optional owner extraction and mailbox transport remain separate. Historical reports retain their recorded compiler/source scope.

The [owned-pool example](region-pool.cod) selects Pool through its adapter, obtains the associated factory, and holds its `owned region :Pool` in a lexical scope. The factory initializes its root and both arrays before returning. [Native evidence](owned-pool-validation.json) covers four partial-construction failures with exact cleanup, 10,000 bounded reuse laps and independent inspection/reuse of the 144-byte image after freeing the original. The caller-region overload remains available; no new allocation-policy intrinsic is needed.

Regional failures retain the primary error and add source notes identifying the relevant acquisitions. A cross-region stored edge shows the destination object's owner and referenced target's owner; an escaping result identifies the region it would outlive. Fold/conditional owner conflicts distinguish their input paths, and prohibited dynamic extraction identifies the held resource. This is compiler metadata, with no runtime layout change. [Diagnostic evidence](region-diagnostics-validation.json) records twelve focused checks, including six existing negative fixtures that assert the acquisition locations and five valid borrowing/mutation/capture/dispatch examples.

## Module and storage boundary

All dependency files are parsed before any execution is emitted. A syntax or required-binding error rejects the whole entry before any top-level print can run. Procedure registration during scanning does not capture values; capture occurs at its definition event in the resulting execution.

After the complete scan, the first cross-module encounter incorporates that module’s top-level runtime semantics into the resulting program. Later `symbol from`, `using`, `import` and `mixin` encounters reuse the incorporated module and its resources. Its top-level context and still-held regions remain live until normal process exit under H-166; returning from initialization restores the incorporating module’s active lookup context without releasing those owners. Identity-only selection does not retain an incidental runtime value; selected procedures retain captured bits and regional-reference values; a reference does not extend its region lifetime or copy its target. Imported aliases must have reached their `symbol from` or introducing `using symbol` encounter before use, including direct symbol references in procedure definitions. Combined using is one source encounter; matching an existing identity still installs the selected procedure. A body map does not rewrite source initialization or other existing procedures.

Unknown local suppliers/source-body roles and duplicate mapping roles are diagnosed. Splitting aliases of one source identity across multiple receiving identities is outside the prototype; mapping them to one identity is supported. Broader mapping policy remains open.

The subset accepts acyclic module composition including shared and diamond dependencies. Each module is incorporated once, in first-encounter order; its effects are not rerun or recaptured for another caller. A demanded initialization cycle is diagnosed; general cyclic-initialization semantics remain open. Compiler encounters do not execute user code.

Local symbol identity uses the canonical module path and declaration, preserving aliases and separating distinct source files. Versioned package identity and first-class runtime symbol selection are not implemented. Checked native adapters support runtime-selected callable values, recursive calls, higher-order arguments and complete callable results within [D-18's implemented boundaries](../../../design/RegionalClosures.md#implementation-status-and-review-boundaries). Unqualified owner-bound scalar result staging and broader result/context combinations remain incomplete.

The generated program uses fixed thread-local typed binding slots and stack-based saved values. Native procedures are specialized for checked contexts. Callable images and defer records may use runtime-sized backing released by their lexical owner; this does not introduce an independently managed user heap lifetime. Regional user objects retain region-only allocation. Regional references carry offsets with owning-region information specialized along the known WPO path. Persisted intra-region fields use shilos `regional_ptr`; source-level cross-region fields and persistent closures remain unsupported. The presence of TLS does not establish tested multi-thread or reentrant execution support.
