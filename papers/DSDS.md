# Domain-Specific Database Solutions in CoD — Direct Access and Native DML with DBMR

*Working paper, first draft. The proposed server interface and DML service are research directions. The [application guide](../docs/BuildingADatabaseServiceInCoD.md) works through the reservation. [Design authority and scope](../design/DesignAuthorityRegistry.md#d-dbmr-service-research).*

Two orders arrive for an edition that requires plates A and B and a foldout F. The warehouse has one F left. Both clerks should be able to consult the same large catalog. At most one can receive a confirmed reservation. Tomorrow a bibliographer might correct the catalog. The warehouse must still explain what yesterday's customer reserved.

Can a domain team meet these requirements with one set of CoD types, direct access to indexed data and a data manipulation language (DML) composed in CoD? The hypothesis is that this combination can lower the cost of building **and owning** domain-specific database solutions. The team gets to choose what travels together, what commits together and which observations may lag. Its choices still need a database contract and evidence.

## Publish the access paths with the data

A disk-backed memory region (DBMR) can hold a typed directed graph admitting cycles (DCG). Give the catalog a B+ tree keyed by edition. A leaf points to E42, whose ordered constituent occurrences point to canonical sheet records. If a plate occurs twice, two occurrences point to the same plate. Deduplicating those pointers would give a wrong picking list. A reverse index from a sheet to its occurrences answers a different question for editors reviewing a correction. Check each index against the underlying facts, including order and multiplicity. A well-typed pointer can still lead to the wrong sheet. [Shared facsimile catalog](AlgebraicEffectsIsAllYouNeed.md#shared-ontology-packages-and-dbmr-databases)

Warehouse and editorial processes can open the same published revision at different addresses. Relative edges preserve the graph without per-edge repair. Each opening has its own actual owner. The service can also consult an independently versioned assembly ontology, keep frequent stock and reservation writes in one or more small online transaction processing (OLTP) databases, and use in-memory regions for request-local work. Persistent reservations record domain keys and the ontology revisions they used. Retaining those revisions lets a later reader reconstruct the picking list. Direct edges stay inside their owning region. [Graph boundaries](../design/GraphGrainedMemoryManagement.md#relationships-between-regions)

## Send a DML program to the records it changes

The clerk's client uses CoD library operations to compose a request that resolves E42, gathers required quantities, checks stock, reserves the complete set and projects a receipt. Changing the projection can reuse the same instructions and endpoint. The client builds a self-contained packet region of typed instructions, inputs and keys. Once the Actor transport admits a complete, compatible packet, a server-side high-level virtual machine (HLVM) interprets it with the databases and effects the service grants. The reply carries a separate region with receipt values or a business refusal. Its contents remain usable after the server releases the request.

Shared domain vocabulary serves direct traversal, DML construction and result consumption. This native path needs no object–relational or object–graph mapper. The client chooses its result projection from the shared instruction vocabulary. The server checks the packet's compatibility and decides which operations it admits. Published DBMRs already have a confirmed immutable-access and fresh-name publication design. A proposed **server-specific advanced DBMR interface** would allow writable reopening of designated database backing. Its contract must define mapping identity, view validity during remapping, write visibility, flush and failure behavior. The database service owns transaction coordination across processes. Actor execution and the writable interface are prerequisites for evaluating the service. [DBMR modes](../design/ConstructionAndAcquisition.md#dbmr-modes) · [Packet admission](../design/ActorChannels.md#regional-transport-over-akcp)

## Give each observation a consistency contract

For the authoritative reservation, **atomicity** covers every debit and the reservation record. **Consistency** requires nonnegative stock and a recorded quantity for every required occurrence. **Isolation** must prevent two server processes that each read the last F from both committing it. **Durability** specifies which failures an acknowledged reservation survives. One writable DBMR is a natural boundary for this transaction. If stock and reservations occupy separate writable DBMRs, the server must commit their changes as a unit to offer the same guarantee. A lost reply leaves the client unsure of the outcome. In a retryable protocol, committing a request identity and its result with the debit lets the client recover its prior outcome. [Application, commit and retry](../design/DomainLanguageDesign.md#dl-05)

An availability display may promise **eventual consistency**. After the last commit, once communication resumes and the display has applied the outstanding changes, it should agree with authoritative stock. It may show one F while a reservation has already taken it. The server checks authoritative inventory before confirmation. Specify how the display catches up following disconnection and how replay handles duplicate or reordered updates. This permits a stale display alongside an ACID reservation. A different domain operation can also accept writes at disconnected sites. For example, two editors can each append an independently identified observation about E42. If the agreed result is the union of observations, merging by unique assertion ID preserves both, including disagreements. Deciding which assertion becomes the approved catalog entry is a separate operation with its own rule. [Coordination and application invariants](https://www.vldb.org/pvldb/vol8/p185-bailis.pdf)

## What would establish lower ownership cost?

ObjectStore studied direct programmatic access to persistent objects. GRainDB studied predefined join paths, including when sequential scans outperform traversal. Compare equivalent answers against an indexed relational implementation using the same transaction and recovery promises. Measure cold validation and opening, first and repeated lookups, commit latency, bytes written and recovery time. Count schema migrations, adapters, server changes and operational work when adding a second ontology or a DML projection. Charge the domain solution for maintaining its own indexes and transaction machinery. [ObjectStore](https://cs.stanford.edu/people/chrismre/cs345/rl/lamb91.pdf) · [GRainDB](https://www.vldb.org/pvldb/vol15/p1011-jin.pdf)

Acceptance starts with two competing processes, a lost reply after commit, a lagging display that catches up, and a historical receipt still interpretable after a catalog correction. If the catalog gains a missing sheet K tomorrow, opening yesterday’s pinned revision must still explain the original A/F/B receipt. The advanced interface, crash-recovery algorithms and comparative measurements of technical debt and operating cost remain future work.
